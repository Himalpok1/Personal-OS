| ADR-041 | The Personal OS Daily Brief is **manual/on-demand only**: deterministic bounded collector → single provider-agnostic LLM call through the existing `ai_task_routes` layer (`task_name='daily_brief'`) with an explicit abort timeout, output-token cap, injection-guarded prompt, structured graceful degradation when no provider is configured, and persistence unique per `(brief_date, timezone)`. **No queue, no cron, no scheduled or autonomous agents** in Phase 5. | ADR-042 | **Canonical all-day event recurrence.** An all-day event's `start_date`/`end_date` are authoritative and `starts_at`/`ends_at` remain NULL — `starts_at` is **never** written for an all-day event, including to make recurrence work. The recurrence engine anchors an all-day series' DTSTART at **local noon** derived from `start_date` (the convention already documented on `DueDateRecurrenceRule.dtstart` but previously unused), which is DST-safe and correct in nonexistent-midnight zones such as America/Santiago. One shared builder, `buildEventRecurrenceRule` in `packages/core/src/recurrence/event-recurrence.ts`, is the **only** place a stored event row becomes a recurrence rule, and on-demand expansion (`assembleEventRange`), nightly worker materialization, create/PATCH materialization, and occurrence-validity checks (`isValidOccurrence`) all use it — a split-brain recurrence model is forbidden. For `is_recurring_instance && all_day`, `EventRangeItem.start_date`/`end_date` are **re-pointed to that instance's actual calendar dates** (preserving the template's day-span), deliberately asymmetric with timed instances (whose `starts_at`/`ends_at` stay the series template and are positioned by `occurs_at`), because the frozen `EventRangeItem`/`TodayEventItem`/`AgendaItem` shapes carry no per-instance date field and the instance date would otherwise be inexpressible. Pure calendar dates never round-trip through a UTC instant (Checkpoint 5.4, user-approved 2026-08-22) | Locked |
| ADR-043 | **Daily Brief implementation clarification (extends ADR-041, does not supersede it).** Routes are `POST /briefs` (body `{tz}`, honoring the already-frozen `BriefRequestSchema`) and `GET /briefs/current?tz=`, which **never generates** — a missing brief is `404 not_found`, normalized client-side to null per the `/reviews/latest` convention. Persisted identity is `(brief_date, timezone)` where `brief_date` is the **requested timezone's local calendar date** derived from `localDayWindow(tz, effectiveNow).localDate`, never by UTC-slicing an instant; regeneration upserts that same row and no brief history is kept. The deterministic collector **derives from `buildTodayResponse`** rather than re-deriving Today's rules, so a brief can never narrate numbers that contradict the Today screen; `buildTodayResponse` gained an **internal-only** optional `now` seam that is deliberately absent from `TodayQuerySchema` so no HTTP client can pin or spoof the clock. Secret exclusion is **structural**: the model only ever sees `BriefInput`, a closed scalar allowlist carrying no ids, no uuids, no free-text bodies and no credential-bearing field, so a secret is inexpressible rather than merely discouraged. The server **owns the persisted output shape** — only `{ text }` built from the model's prose is stored, never arbitrary model-returned fields, despite `BriefContentSchema` being `.passthrough()`. Timeout model is **30 s per attempt under a 45 s whole-chain budget**, each attempt receiving a fresh `AbortSignal` and no candidate being attempted once the budget is spent. Error taxonomy: `409 no_provider_configured`, `504 brief_generation_timeout`, `502 brief_generation_failed`, `400 validation_failed`; because `setErrorHandler` only passes 4xx through, the 5xx codes are replied explicitly by the route. `ai_daily_briefs.model_id` records the ai_models row that **actually served** the call via the new `callWithFallbackTracked`, never the route's primary assumed after the fact. Generation is synchronous and manual: no queue, no cron, no tools, no push (Checkpoint 5.5, 2026-08-23) | Locked |
| ADR-044 | **Production `daily_brief` route reuses the existing `gpt-4.1` model row** (`313633f4-2c52-4a06-a696-4f7740a95f28`, connection `My OpenAI`), primary-only with no fallback — no new provider connection, no new `ai_models` row and no credential handling. Chosen over a cheaper dedicated model or the Groq connection because it adds zero new credential surface and the model is already proven in production for capture parsing; cost is negligible at manual on-demand cadence. Note there is **no DELETE endpoint for task routes**, so reverting requires another upsert repointing `primary_model_id` or direct SQL. Phase 5 deployment also establishes that production releases build from a **per-release source directory** (`/home/himallinux/personal-os-<checkpoint>-release`, shipped via `git archive`) with the stable `.env` at `/home/himallinux/personal-os/.env`, which removes the Checkpoint 4.7 `rsync --delete` deletion-manifest hazard; and that **images must be built before migrations are applied**, because the migration runs from the api image (Checkpoint 5.7, user-approved 2026-08-24) | Locked |
| ADR-045 | **The local-noon recurrence anchor is implementation metadata and must never reach presentation.** ADR-042 anchors a recurring all-day series' DTSTART at local noon for DST safety; ADR-045 states the consequence: `all_day === true` means date-only everywhere outside recurrence internals — never format, position, or narrate `occurs_at` for an all-day item. Presentation code uses the instance's `start_date`/`end_date`, which `assembleEventRange` already re-points per instance. `BriefEventItem` carries `date` and its `starts_at` is always null when `all_day` is true, so a time is *inexpressible* rather than merely discouraged; the Brief system prompt states the rule explicitly as defense in depth; and the decision lives in one shared helper (`apps/mobile/src/utils/event-time-label.ts`) used by both Today and Agenda so the chains cannot drift. Google/CalDAV semantics are explicitly out of scope — sync reads `events` rows directly and has zero references to the presentation projections (Checkpoint 5.7.1, 2026-08-24) | Locked |
| ADR-046 | **Phase 6 is Google Health cloud integration, read-only, server-side.** Supersedes the `ARCHITECTURE.md` phase-plan entry for Phase 6 only: **Apple HealthKit, `@kingstinct/react-native-healthkit`, Android Health Connect and `react-native-health-connect` are removed from scope entirely** — no native health access, no device-local health sync, no Apple Developer dependency. Personal OS reads the **Google Health API** (`health.googleapis.com`, `/v4`) over OAuth 2.0 with **exactly three read-only scopes** (`activity_and_fitness.readonly`, `sleep.readonly`, `health_metrics_and_measurements.readonly`), synchronised by `apps/worker` into PostgreSQL and rendered by the existing Expo client. The legacy Fitbit Web API is **not** a target and no dual Fitbit/Google migration layer is built — there are no existing Fitbit tokens to migrate. **Webhooks are permanently excluded under ADR-018**: the documented subscriber endpoint *"must use HTTPS (TLSv1.2+) and be publicly accessible"*, and this project adds no public ingress. Because the API documents **no sync token, no `updateTime` filter, no `showDeleted` and no tombstones** — and `reconcile` is multi-source de-duplication, not change tracking — synchronisation is a **bounded trailing-window re-fetch with per-row content hashing**. This carries an explicit, accepted **35-day staleness contract**: an upstream edit or deletion older than the warm window is invisible until an explicit re-verify. Densification (writing `has_data=false` for a verified-absent day) is permitted on **warm/manual/backfill only, never `hot`**, is skipped entirely when a chunk returns zero buckets, and is clamped to dates at or after the first date that has ever returned data — so a transient empty response cannot blank real data and a backfill cannot manufacture verified-absent history for months before the device existed (Phase 6 Checkpoint 6.0, user-approved 2026-08-24) | Locked |
| ADR-047 | **Health storage is daily aggregates plus sessions; intraday is heart-rate only; nothing is auto-deleted.** Phase 6A stores one `health_daily_metrics` row per `(connection, metric, local_date)`, session rows for `sleep`/`exercise`, and **intraday samples for `heart-rate` alone** — every other metric is acquired at daily or session granularity, which also makes the types that expose **no `list` operation at all** (`total-calories`, `calories-in-heart-rate-zone`, `floors`) first-class rather than special cases. Units are **metric-implied** (the API bakes them into field names), so no unit column exists; per-metric semantics are enforced in Zod against a code catalog, while Postgres enforces shape and identity. **True zero and missing are structurally distinct** — a CHECK makes their collapse impossible — and **no read model, aggregate or brief collector may ever `COALESCE(value, 0)`**. **No health data is ever automatically deleted, expired or pruned.** Any retention policy is a separate, explicitly-approved decision and would ship disabled by default; only operational metadata (`health_sync_runs`, expired OAuth states) is swept (Phase 6 Checkpoint 6.0, user-approved 2026-08-24) | Locked |
| ADR-048 | **`local_date` is the API's civil date; no timezone is stored; the sync window is UTC-computed and widened.** `DailyRollupDataPoint` documents `civilStartTime`/`civilEndTime`, so `local_date` is taken **verbatim from `civilStartTime.date`** — Personal OS never converts an instant to a date and therefore **stores no IANA timezone for health data**, which makes DST and travel correct by construction rather than by arithmetic. The honest consequence is that `local_date` is *the device's* civil date, not the user's calendar date in a chosen zone; during travel they can disagree by a day, and the device's answer is the physically honest one. `dailyRollUp` supplies **no physical instants and no UTC offsets**, so daily rows carry none — and therefore **duration-normalized daily rates are not derivable** and are not offered (a civil day is 23, 24 or 25 hours; a rate view would require a `rollUp` call with an explicit `windowSize`, which is a separate scoped addition). Because no zone is stored, the **sync window** needs its own defined clock: it is computed in UTC and **widened one calendar day at each end**, and the two boundary days are **never densified** — any offset on Earth falls strictly inside a one-day widening, so no real local day escapes the window and no partially-elapsed local day is recorded as empty. **ADR-042's local-noon anchor and ADR-045's presentation rule are explicitly NOT reused**: they exist because the recurrence engine must synthesize an instant from a bare date, whereas the Health API supplies civil date, physical instant and offset independently. Health has no recurrence, no RRULE, no window expansion and no all-day concept, and no health table has a foreign key into the calendar graph (Phase 6 Checkpoint 6.0, user-approved 2026-08-24) | Locked |
| ADR-049 | **A sleep session is attributed to, and queried on, its civil END (wake) date.** `attributed_local_date = civilEndTime.date`; exercise is attributed to its civil **start** date. Three reasons, the second decisive: it matches the mental model ("how did I sleep last night?" is asked the morning after); the `daily-*` types computed from the sleep period (`daily-resting-heart-rate`, `daily-heart-rate-variability`, `daily-sleep-temperature-derivations`) are reported by Google on one civil date, so wake-date attribution is what keeps a `sleep`-to-`daily-hrv` join from being off by one; and it is total, since every session has a civil end date. **The API makes this free rather than merely convenient**: `list` documents `sleep.interval.end_time` / `sleep.interval.civil_end_time` as sleep-exclusive filters and explicitly excludes sleep from the generic session-start filter, so the attribution rule, the fetch filter and the deletion-reconciliation scope are **one and the same axis** — no start-time query with a compensating one-day widening is needed or correct. The rule lives in exactly one function (`packages/core/src/health/day-attribution.ts`) and **every input is stored**, so changing it is a local `UPDATE` plus re-derivation with no re-fetch and no migration (Phase 6 Checkpoint 6.0, user-approved 2026-08-24) | Locked |
| ADR-050 | **CHECK constraints only on vocabularies this project fully controls and that are closed by design.** `status`, `backfill_status`, sync-run `kind`/`status`, `external_key_source` and structural invariants (including all-or-nothing completeness of every encrypted credential triple) are CHECKed. `provider`, `metric`, `source_family` and `failure_class` are **not** — they are provider-defined or expected to grow, and are Zod-enforced instead. The reason is concrete and local: `packages/db/scripts/reconcile-drizzle-tracking.ts` understands `ADD CONSTRAINT ... CHECK` but **not** `DROP CONSTRAINT`, so widening a CHECK later forces a hand-written, unreconcilable migration — which is exactly what `0009_caldav_provider_support.sql` did and exactly why that reconcile script had to be written. Adding a health metric or a second health provider must never require repeating that (Phase 6 Checkpoint 6.0, user-approved 2026-08-24) | Locked |
