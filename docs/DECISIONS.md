| ADR-042 | **Canonical all-day event recurrence.** An all-day event's `start_date`/`end_date` are authoritative and `starts_at`/`ends_at` remain NULL — `starts_at` is **never** written for an all-day event, including to make recurrence work. The recurrence engine anchors an all-day series' DTSTART at **local noon** derived from `start_date` (the convention already documented on `DueDateRecurrenceRule.dtstart` but previously unused), which is DST-safe and correct in nonexistent-midnight zones such as America/Santiago. One shared builder, `buildEventRecurrenceRule` in `packages/core/src/recurrence/event-recurrence.ts`, is the **only** place a stored event row becomes a recurrence rule, and on-demand expansion (`assembleEventRange`), nightly worker materialization, create/PATCH materialization, and occurrence-validity checks (`isValidOccurrence`) all use it — a split-brain recurrence model is forbidden. For `is_recurring_instance && all_day`, `EventRangeItem.start_date`/`end_date` are **re-pointed to that instance's actual calendar dates** (preserving the template's day-span), deliberately asymmetric with timed instances (whose `starts_at`/`ends_at` stay the series template and are positioned by `occurs_at`), because the frozen `EventRangeItem`/`TodayEventItem`/`AgendaItem` shapes carry no per-instance date field and the instance date would otherwise be inexpressible. Pure calendar dates never round-trip through a UTC instant (Checkpoint 5.4, user-approved 2026-08-22) | Locked |
| ADR-043 | **Daily Brief implementation clarification (extends ADR-041, does not supersede it).** Routes are `POST /briefs` (body `{tz}`, honoring the already-frozen `BriefRequestSchema`) and `GET /briefs/current?tz=`, which **never generates** — a missing brief is `404 not_found`, normalized client-side to null per the `/reviews/latest` convention. Persisted identity is `(brief_date, timezone)` where `brief_date` is the **requested timezone's local calendar date** derived from `localDayWindow(tz, effectiveNow).localDate`, never by UTC-slicing an instant; regeneration upserts that same row and no brief history is kept. | ADR-046 | **Phase 6 is Google Health cloud integration, read-only, server-side.** Supersedes the `ARCHITECTURE.md` phase-plan entry for Phase 6 only: **Apple HealthKit, `@kingstinct/react-native-healthkit`, Android Health Connect and `react-native-health-connect` are removed from scope entirely** — no native health access, no device-local health sync, no Apple Developer dependency. | ADR-047 | **Health storage is daily aggregates plus sessions; intraday is heart-rate only; nothing is auto-deleted.** Phase 6A stores one `health_daily_metrics` row per `(connection, metric, local_date)`, session rows for `sleep`/`exercise`, and **intraday samples for `heart-rate` alone** — every other metric is acquired at daily or session granularity, which also makes the types that expose **no `list` operation at all** (`total-calories`, `calories-in-heart-rate-zone`, `floors`) first-class rather than special cases. | ADR-048 | **`local_date` is the API's civil date; no timezone is stored; the sync window is UTC-computed and widened.** `DailyRollupDataPoint` documents `civilStartTime`/`civilEndTime`, so `local_date` is taken **verbatim from `civilStartTime.date`** — Personal OS never converts an instant to a date and therefore **stores no IANA timezone for health data**, which makes DST and travel correct by construction rather than by arithmetic. The honest consequence is that `local_date` is *the device's* civil date, not the user's calendar date in a chosen zone; during travel they can disagree by a day, and the device's answer is the physically honest one. `dailyRollUp` supplies **no physical instants and no UTC offsets**, so daily rows carry none — and therefore **duration-normalized daily rates are not derivable** and are not offered (a civil day is 23, 24 or 25 hours; a rate view would require a `rollUp` call with an explicit `windowSize`, which is a separate scoped addition). Because no zone is stored, the **sync window** needs its own defined clock: it is computed in UTC and **widened one calendar day at each end**, and the two boundary days are **never densified** — any offset on Earth falls strictly inside a one-day widening, so no real local day escapes the window and no partially-elapsed local day is recorded as empty. **ADR-042's local-noon anchor and ADR-045's presentation rule are explicitly NOT reused**: they exist because the recurrence engine must synthesize an instant from a bare date, whereas the Health API supplies civil date, physical instant and offset independently. Health has no recurrence, no RRULE, no window expansion and no all-day concept, and no health table has a foreign key into the calendar graph (Phase 6 Checkpoint 6.0, user-approved 2026-08-24) | Locked |
| ADR-049 | **A sleep session is attributed to, and queried on, its civil END (wake) date.** `attributed_local_date = civilEndTime.date`; exercise is attributed to its civil **start** date. Three reasons, the second decisive: it matches the mental model ("how did I sleep last night?" is asked the morning after); the `daily-*` types computed from the sleep period (`daily-resting-heart-rate`, `daily-heart-rate-variability`, `daily-sleep-temperature-derivations`) are reported by Google on one civil date, so wake-date attribution is what keeps a `sleep`-to-`daily-hrv` join from being off by one; and it is total, since every session has a civil end date. **The API makes this free rather than merely convenient**: `list` documents `sleep.interval.end_time` / `sleep.interval.civil_end_time` as sleep-exclusive filters and explicitly excludes sleep from the generic session-start filter, so the attribution rule, the fetch filter and the deletion-reconciliation scope are **one and the same axis** — no start-time query with a compensating one-day widening is needed or correct. The rule lives in exactly one function (`packages/core/src/health/day-attribution.ts`) and **every input is stored**, so changing it is a local `UPDATE` plus re-derivation with no re-fetch and no migration (Phase 6 Checkpoint 6.0, user-approved 2026-08-24) | Locked |

| ADR-046a | **Amendment to ADR-046 (2026-08-25, Checkpoint 6.3, user-approved): authoritative zero-bucket daily densification is permitted.** ADR-046's blanket rule -- densification "is skipped entirely when a chunk returns zero buckets" -- was written in Checkpoint 6.0, when nothing could distinguish an authoritatively-empty window from a transiently-empty one. Checkpoint 6.3's authority model can: `authoritative = fetchComplete && rejections === 0 && kind !== 'hot'`. | ADR-053 | **Mail integration is Gmail, `gmail.metadata` only, cursor-based, and polled.** Exactly one scope is requested: `https://www.googleapis.com/auth/gmail.metadata` — message ids, thread ids, labels and headers. **`gmail.readonly` is deliberately not requested.** Both are classified **Restricted** by Google, so the narrower scope buys no verification or CASA relief; what it buys is that **no message body, snippet, payload part or attachment is ever fetched or stored**, which removes the retention question entirely (ADR-054) and reduces the attacker-authored surface to a subject line and a sender display name. Two documented costs are accepted: the `q` search parameter is rejected under this scope (`403 Metadata scope does not support 'q' parameter`), so scoping is by `labelIds` — which covers `INBOX`/`UNREAD`/`IMPORTANT`/`STARRED`/`CATEGORY_*` and is sufficient — and `format=FULL`/`RAW` are rejected, which is the point rather than a limitation. Identity and the bootstrap cursor both come from a single `users.getProfile` call, which returns `emailAddress` **and** `historyId` under this scope alone, so **no `openid`/`email` scope is added** and the Phase 4 `id_token` path is not reused. **The cursor is an opaque provider token, not a date, and this deliberately inverts `health_metric_streams.backfill_cursor_date`'s "a date, never a page token" rule**: `historyId` is the only incremental primitive Gmail offers and it *does* expire — `history.list` returns **HTTP 404** once `startHistoryId` falls outside a retention window documented only as "at least one week and often longer". Cursor expiry is therefore a **first-class, tested state transition** (`needs_full_resync` → bounded full sync → new cursor), never an edge case. Authorization uses a **third OAuth client in the existing `personal-os-196cf` project** — never a second project, per ADR-051 — following the Calendar/Health precedent that a token minted for one integration is never reused for another. The shared limiter is copied from `packages/health-providers/src/sync/limiter.ts` but **honours `Retry-After`**, which Gmail and Graph both send and the Google Health API does not; ADR-046's blind-full-jitter reasoning is explicitly not carried over. **`Retry-After` behaviour is proven by deterministic testing** — injected responses against the limiter's already-injected `now`/`sleep`/`random` seams, asserting exact millisecond values — and **a real Gmail 429 is not required for acceptance**, because provoking one would mean deliberately abusing the quota.
