| ADR-042 | **Canonical all-day event recurrence.** An all-day event's `start_date`/`end_date` are authoritative and `starts_at`/`ends_at` remain NULL — `starts_at` is **never** written for an all-day event, including to make recurrence work. The recurrence engine anchors an all-day series' DTSTART at **local noon** derived from `start_date` (the convention already documented on `DueDateRecurrenceRule.dtstart` but previously unused), which is DST-safe and correct in nonexistent-midnight zones such as America/Santiago. One shared builder, `buildEventRecurrenceRule` in `packages/core/src/recurrence/event-recurrence.ts`, is the **only** place a stored event row becomes a recurrence rule, and on-demand expansion (`assembleEventRange`), nightly worker materialization, create/PATCH materialization, and occurrence-validity checks (`isValidOccurrence`) all use it — a split-brain recurrence model is forbidden. For `is_recurring_instance && all_day`, `EventRangeItem.start_date`/`end_date` are **re-pointed to that instance's actual calendar dates** (preserving the template's day-span), deliberately asymmetric with timed instances (whose `starts_at`/`ends_at` stay the series template and are positioned by `occurs_at`), because the frozen `EventRangeItem`/`TodayEventItem`/`AgendaItem` shapes carry no per-instance date field and the instance date would otherwise be inexpressible. Pure calendar dates never round-trip through a UTC instant (Checkpoint 5.4, user-approved 2026-08-22) | Locked |
| ADR-043 | **Daily Brief implementation clarification (extends ADR-041, does not supersede it).** Routes are `POST /briefs` (body `{tz}`, honoring the already-frozen `BriefRequestSchema`) and `GET /briefs/current?tz=`, which **never generates** — a missing brief is `404 not_found`, normalized client-side to null per the `/reviews/latest` convention. Persisted identity is `(brief_date, timezone)` where `brief_date` is the **requested timezone's local calendar date** derived from `localDayWindow(tz, effectiveNow).localDate`, never by UTC-slicing an instant; regeneration upserts that same row and no brief history is kept. Secret exclusion is **structural**: the model only ever sees `BriefInput`, a closed scalar allowlist carrying no ids, no uuids, no free-text bodies and no credential-bearing field, so a secret is inexpressible rather than merely discouraged. The server **owns the persisted output shape** — only `{ text }` built from the model's prose is stored, never arbitrary model-returned fields, despite `BriefContentSchema` being `.passthrough()`. Timeout model is **30 s per attempt under a 45 s whole-chain budget**, each attempt receiving a fresh `AbortSignal` and no candidate being attempted once the budget is spent. | ADR-046 | **Phase 6 is Google Health cloud integration, read-only, server-side.** Supersedes the `ARCHITECTURE.md` phase-plan entry for Phase 6 only: **Apple HealthKit, `@kingstinct/react-native-healthkit`, Android Health Connect and `react-native-health-connect` are removed from scope entirely** — no native health access, no device-local health sync, no Apple Developer dependency. The legacy Fitbit Web API is **not** a target and no dual Fitbit/Google migration layer is built — there are no existing Fitbit tokens to migrate. **Webhooks are permanently excluded under ADR-018**: the documented subscriber endpoint *"must use HTTPS (TLSv1.2+) and be publicly accessible"*, and this project adds no public ingress. Because the API documents **no sync token, no `updateTime` filter, no `showDeleted` and no tombstones** — and `reconcile` is multi-source de-duplication, not change tracking — synchronisation is a **bounded trailing-window re-fetch with per-row content hashing**. Densification (writing `has_data=false` for a verified-absent day) is permitted on **warm/manual/backfill only, never `hot`**, is skipped entirely when a chunk returns zero buckets, and is clamped to dates at or after the first date that has ever returned data — so a transient empty response cannot blank real data and a backfill cannot manufacture verified-absent history for months before the device existed (Phase 6 Checkpoint 6.0, user-approved 2026-08-24) | Locked |
| ADR-047 | **Health storage is daily aggregates plus sessions; intraday is heart-rate only; nothing is auto-deleted.** Phase 6A stores one `health_daily_metrics` row per `(connection, metric, local_date)`, session rows for `sleep`/`exercise`, and **intraday samples for `heart-rate` alone** — every other metric is acquired at daily or session granularity, which also makes the types that expose **no `list` operation at all** (`total-calories`, `calories-in-heart-rate-zone`, `floors`) first-class rather than special cases. Units are **metric-implied** (the API bakes them into field names), so no unit column exists; per-metric semantics are enforced in Zod against a code catalog, while Postgres enforces shape and identity. **True zero and missing are structurally distinct** — a CHECK makes their collapse impossible — and **no read model, aggregate or brief collector may ever `COALESCE(value, 0)`**. **No health data is ever automatically deleted, expired or pruned.** Any retention policy is a separate, explicitly-approved decision and would ship disabled by default; only operational metadata (`health_sync_runs`, expired OAuth states) is swept (Phase 6 Checkpoint 6.0, user-approved 2026-08-24) | Locked |
| ADR-048 | **`local_date` is the API's civil date; no timezone is stored; the sync window is UTC-computed and widened.** `DailyRollupDataPoint` documents `civilStartTime`/`civilEndTime`, so `local_date` is taken **verbatim from `civilStartTime.date`** — Personal OS never converts an instant to a date and therefore **stores no IANA timezone for health data**, which makes DST and travel correct by construction rather than by arithmetic. The honest consequence is that `local_date` is *the device's* civil date, not the user's calendar date in a chosen zone; during travel they can disagree by a day, and the device's answer is the physically honest one. `dailyRollUp` supplies **no physical instants and no UTC offsets**, so daily rows carry none — and therefore **duration-normalized daily rates are not derivable** and are not offered (a civil day is 23, 24 or 25 hours; a rate view would require a `rollUp` call with an explicit `windowSize`, which is a separate scoped addition). Because no zone is stored, the **sync window** needs its own defined clock: it is computed in UTC and **widened one calendar day at each end**, and the two boundary days are **never densified** — any offset on Earth falls strictly inside a one-day widening, so no real local day escapes the window and no partially-elapsed local day is recorded as empty. **ADR-042's local-noon anchor and ADR-045's presentation rule are explicitly NOT reused**: they exist because the recurrence engine must synthesize an instant from a bare date, whereas the Health API supplies civil date, physical instant and offset independently. Health has no recurrence, no RRULE, no window expansion and no all-day concept, and no health table has a foreign key into the calendar graph (Phase 6 Checkpoint 6.0, user-approved 2026-08-24) | Locked |
| ADR-049 | **A sleep session is attributed to, and queried on, its civil END (wake) date.** `attributed_local_date = civilEndTime.date`; exercise is attributed to its civil **start** date. Three reasons, the second decisive: it matches the mental model ("how did I sleep last night?" is asked the morning after); the `daily-*` types computed from the sleep period (`daily-resting-heart-rate`, `daily-heart-rate-variability`, `daily-sleep-temperature-derivations`) are reported by Google on one civil date, so wake-date attribution is what keeps a `sleep`-to-`daily-hrv` join from being off by one; and it is total, since every session has a civil end date. **The API makes this free rather than merely convenient**: `list` documents `sleep.interval.end_time` / `sleep.interval.civil_end_time` as sleep-exclusive filters and explicitly excludes sleep from the generic session-start filter, so the attribution rule, the fetch filter and the deletion-reconciliation scope are **one and the same axis** — no start-time query with a compensating one-day widening is needed or correct. The rule lives in exactly one function (`packages/core/src/health/day-attribution.ts`) and **every input is stored**, so changing it is a local `UPDATE` plus re-derivation with no re-fetch and no migration (Phase 6 Checkpoint 6.0, user-approved 2026-08-24) | Locked |

| ADR-046a | **Amendment to ADR-046 (2026-08-25, Checkpoint 6.3, user-approved): authoritative zero-bucket daily densification is permitted.** ADR-046's blanket rule -- densification "is skipped entirely when a chunk returns zero buckets" -- was written in Checkpoint 6.0, when nothing could distinguish an authoritatively-empty window from a transiently-empty one. Checkpoint 6.3's authority model can: `authoritative = fetchComplete && rejections === 0 && kind !== 'hot'`. A **fully fetched, rejection-free, non-hot daily window returning zero buckets may therefore create verified-absence rows** (`has_data = false`). Strictly bounded: those writes are **insert-only** and may never overwrite or downgrade an existing `has_data = true` row; they remain clamped by `first_data_date` at the start and `lastGloballyCompleteDateExclusive(now)` at the end, so neither pre-device history nor a still-in-flight civil day can be stamped verified-absent; an incomplete, rejected, `hot` or otherwise non-authoritative empty response writes **nothing**; and later real data may replace a `has_data = false` marker. **This amendment applies only to daily-metric densification.** An empty session key set still cannot trigger tombstoning (ADR-047a) -- `x <> ALL('{}'::text[])` is TRUE in Postgres, so an ungated empty sweep would tombstone an entire window. | ADR-053 | **Mail integration is Gmail, `gmail.metadata` only, cursor-based, and polled.** Exactly one scope is requested: `https://www.googleapis.com/auth/gmail.metadata` — message ids, thread ids, labels and headers. **`gmail.readonly` is deliberately not requested.** Both are classified **Restricted** by Google, so the narrower scope buys no verification or CASA relief; what it buys is that **no message body, snippet, payload part or attachment is ever fetched or stored**, which removes the retention question entirely (ADR-054) and reduces the attacker-authored surface to a subject line and a sender display name. Two documented costs are accepted: the `q` search parameter is rejected under this scope (`403 Metadata scope does not support 'q' parameter`), so scoping is by `labelIds` — which covers `INBOX`/`UNREAD`/`IMPORTANT`/`STARRED`/`CATEGORY_*` and is sufficient — and `format=FULL`/`RAW` are rejected, which is the point rather than a limitation. Identity and the bootstrap cursor both come from a single `users.getProfile` call, which returns `emailAddress` **and** `historyId` under this scope alone, so **no `openid`/`email` scope is added** and the Phase 4 `id_token` path is not reused. **The cursor is an opaque provider token, not a date, and this deliberately inverts `health_metric_streams.backfill_cursor_date`'s "a date, never a page token" rule**: `historyId` is the only incremental primitive Gmail offers and it *does* expire — `history.list` returns **HTTP 404** once `startHistoryId` falls outside a retention window documented only as "at least one week and often longer". Cursor expiry is therefore a **first-class, tested state transition** (`needs_full_resync` → bounded full sync → new cursor), never an edge case. Authorization uses a **third OAuth client in the existing `personal-os-196cf` project** — never a second project, per ADR-051 — following the Calendar/Health precedent that a token minted for one integration is never reused for another. The shared limiter is copied from `packages/health-providers/src/sync/limiter.ts` but **honours `Retry-After`**, which Gmail and Graph both send and the Google Health API does not; ADR-046's blind-full-jitter reasoning is explicitly not carried over. **`Retry-After` behaviour is proven by deterministic testing** — injected responses against the limiter's already-injected `now`/`sleep`/`random` seams, asserting exact millisecond values — and **a real Gmail 429 is not required for acceptance**, because provoking one would mean deliberately abusing the quota. Provider failures reach durable columns, the wire and the UI only as a **closed `MailSyncErrorCode` enum typed on the wire schema**, with a `sanitize*` boundary guard so a prose leak is a parse failure rather than a silently-passing string (the Checkpoint 6.5 pattern); every new handler is wrapped in a `withMailJobErrorContainment` before registration. **Digests are global across all active connected mailboxes** — one digest per `(digest_date, timezone)` covering every connection, never one per mailbox, because the product question is "what needs my attention today", which is not per-account. **Digest generation and notification are separate concerns**: generation always occurs on schedule and always persists, and **quiet hours delay the notification rather than suppressing it forever** — the existing router drops a quiet-hours notification with no log row, which for a recurring digest would mean silently sending nothing, permanently (Phase 7 Checkpoint 7.0, user-approved 2026-08-30) | Locked |

| ADR-053a | **Amendment to ADR-053 (2026-09-01, Checkpoint 7.8A): EVERY Google authorization this project builds MUST send `include_granted_scopes=true` — Gmail and Google Health alike. The same file already guarded the adjacent hazard, documenting that `prompt=consent` on every reconnect "would slowly destroy older grants — including, in this project, the Calendar and Health ones, which share the same Google account." This is a correctness requirement, not a preference: without it, connecting any one integration destroys the others, and the defect is **reproducible in production** the moment Gmail consent is granted there. **Symmetry is load-bearing, which is why this amendment binds Health as well.** `packages/health-providers/src/google-health-oauth.ts` carried the identical `include_granted_scopes: "false"`, so with Gmail additive and Health not, reauthorizing Health would revoke Gmail and Calendar — the same incident, during the recovery meant to end it. Whether that flow is additive is **unverified**; the evidence only shows its grant can be destroyed BY another consent, not that its own consent destroys others. Until it is proven or changed — a native-module change, hence a new APK and a `versionCode` bump — the operational rule is that **Calendar is reconnected FIRST and the two additive consents follow**, so anything its consent might drop is re-added. **Why this does not violate least privilege.** The scopes Personal OS REQUESTS are unchanged. Mail remains exactly `gmail.metadata` — no `gmail.readonly`, no body, no send, reply, delete, archive, mark-read, move or label, and ADR-052's prohibition on acting on mail is untouched. Health remains exactly ADR-046's three `.readonly` scopes, and still never the fourth (`googlehealth.settings.readonly`) that ADR-046 cut along with paired-device support. Tests now name the forbidden scopes individually on both sides, so a future edit that adds one fails in the suite rather than at a consent screen. What changes is only that the account's other, separately-consented grants survive the transaction. The honest cost, stated rather than discovered: the access token Google returns may now carry previously granted scopes as well, so **Checkpoint 7.2's assertion that Google echoed *exactly* `gmail.metadata` no longer holds** and any test pinning it must be corrected rather than loosened. That is accepted because breadth of scope on a token is not capability exercised — the Gmail client is read-only by construction, exposes no mutation method at all, and calls only Gmail endpoints — and because the alternative is destroying two working integrations, which is a strictly larger loss of the user's own access. **Why a separate Google Cloud project remains rejected.** A second project would give a genuinely independent consent screen and independent grants, and would also fix this. ## Open later-phase decisions

These are intentionally deferred:
