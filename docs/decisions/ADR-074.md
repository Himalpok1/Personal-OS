# ADR-074 — Checkpoint 10.5: exactly one narrow, explicit, nullable FK (tasks.canvas_assignment_id) instead of a generic entity/relationship table (migration 0022)

**Status:** Locked

**Checkpoint 10.5, Foundation lane (2026-09-17, owner-approved).** An architecture review ahead of
this checkpoint considered building a general-purpose entity/relationship graph — a typed edge
table that any future "this X came from this Y" need could reuse without a new migration each
time. **The owner explicitly rejected that shape.** This project already ran that experiment once:
`tags`/`item_tags` (Phase 1) is exactly a generic entity-relationship table, and Checkpoint 10.0's
own codebase-consolidation audit classified it **safe-to-drop** after finding zero rows in
production after a month of live use and zero code references anywhere in the twelve-package
monorepo — the most direct evidence this codebase has that a speculative general relationship
table earns no adoption on its own and just sits as unused surface area (`docs/STATUS.md`,
Checkpoint 10.0 entry: "`tags`/`item_tags` … classified **safe-to-drop**: zero rows in production
after a month of live use, zero code references anywhere"). Building a second, more general version
of the same shape to anticipate future relationships would repeat that exact experiment with no new
evidence that the outcome differs.

**What is approved instead is the opposite of a graph: exactly one relationship, named, typed and
demonstrated.** The product need is concrete and already exists in the running system — Checkpoint
10.1 (ADR-068) already syncs `canvas_assignments` read-only from the owner's real Canvas account,
and the owner wants a task or reminder created from "test on Friday" to say plainly that it came
from that specific assignment, not to be linked by guesswork later. The schema answer is one
nullable foreign key, `tasks.canvas_assignment_id → canvas_assignments.id`, `ON DELETE SET NULL` —
mirroring `tasks.project_id`'s exact shape in the same file, migration `0022_task_canvas_assignment_
link.sql` (level 21 → 22). No join table, no polymorphic `(item_type, item_id)` pair, no generic
`relationships` table with a `kind` discriminator: one column, one index
(`tasks_canvas_assignment_id_idx`, matching the existing `tasks_project_id_idx` immediately above
it), no new CHECK constraint (there is no closed vocabulary here to enforce — ADR-050 is
unimplicated, not merely satisfied).

**The write path is explicit only — no inference, no automatic guessing.** This ADR authorizes the
column and its constraint; it does not authorize the capture parser, a sync job, or any heuristic
to populate it unprompted. Setting `canvas_assignment_id` on a task is something a person or an
explicit, reviewed feature does on purpose, the same discipline ADR-068 §6 already holds Canvas
sync itself to ("no mutations, no new egress surface"). A future feature that wants to *suggest* a
link is free to suggest one — surfaced to the owner for acceptance — but nothing may silently set
this column without a person's explicit action choosing that specific assignment.

**`ON DELETE SET NULL`, not `CASCADE`, for the same reason `tasks.project_id` is `SET NULL`**: a
Canvas assignment can legitimately disappear from the local cache (the owner disconnects Canvas,
an assignment is unpublished and drops out of a resync, `canvas_assignments`' own row is deleted by
some future cleanup) without that ever being a reason to delete the task or reminder built from it.
The task is the owner's own record; the assignment link is provenance, not the task's reason to
exist. Verified empirically against a real Postgres, not merely declared: a task was linked to a
seeded assignment as the least-privilege runtime role (`posops_app`), the assignment row was then
deleted, and the task survived with `canvas_assignment_id` reset to `NULL` — table and row intact,
title intact, only the link cleared.

**A future second relationship gets its own ADR and its own narrow column, never a generalization
of this one.** If a genuine, demonstrated need later arises for "this note came from this mail
thread" or "this event came from this assignment," that is a new, separately-justified nullable FK
with its own migration — not a reason to fold this column into a `(subject_type, subject_id,
object_type, object_id, kind)` edge table. The moment two or three such narrow columns exist is the
moment to *reconsider* whether a generic table would have been cheaper in hindsight; it is not a
reason to build one speculatively now, on the strength of an experiment (`item_tags`) that already
answered the speculative version of that question.

**Migration mechanics, verified empirically, not assumed.** `0022_task_canvas_assignment_link.sql`
is the drizzle-kit-generated shape for this exact schema change — an `ALTER TABLE … ADD COLUMN`, a
separate `ALTER TABLE … ADD CONSTRAINT … FOREIGN KEY`, and a `CREATE INDEX`, matching this
project's own precedent for adding an FK column to an existing table (`0019_event_authoring.sql`'s
`events.origin`/`calendar_connection_calendars.access_role` additions; `0001_foamy_stick.sql`'s
original `tasks_project_id_projects_id_fk`) rather than hand-invented syntax. Before trusting it,
this checkpoint resolved an apparent contradiction in `packages/db/scripts/reconcile-drizzle-
tracking.ts`: its `ADD_COLUMN_DATA_TYPES` allowlist (gating the tool's own bare-`ADD COLUMN` catalog
probe) has, since the file's one commit at Checkpoint 5.3, contained only `text`, `bytea`, `date`
and the two `timestamp` spellings — never `uuid`, and never `real` either, despite migration `0021`
adding a `real` column and `docs/STATUS.md` recording "`db:reconcile` clean" for it. Read against
the tool's own logic (`planReconciliation`) rather than assumed, the contradiction dissolves: a
migration applied the normal way, through `drizzle-kit migrate`, has its tracking row inserted
atomically by drizzle's own migrator in the same run — reconcile then finds that entry already
tracked with `when` at or below the watermark and marks it `SKIP below-watermark` **without ever
deriving a probe for it**. The `ADD_COLUMN_DATA_TYPES` allowlist is reachable only on the
narrower path this script exists for: a migration whose tracking row is missing (the historical
`0009`-applied-via-`psql` incident that motivated writing the tool at all), where reconcile must
independently prove the column already matches the catalog before backfilling a tracking row for
work it did not perform itself.

This was proven against a real, disposable clone of `personalos_test`
(`personalos_test_1054`, dropped at closeout), not simulated: a genuine `drizzle-kit migrate` run
applied `0022` and reconcile (`--check` and write mode) reported **0 discrepancies**, `0022` marked
`SKIP below-watermark` exactly like `0021` before it — the real, only-supported deployment path
(`docs/ARCHITECTURE.md`'s frozen migration order runs `drizzle-kit migrate` directly, never this
reconciler) applies and tracks this migration cleanly. Separately, to resolve the allowlist question
on its own terms rather than leave it theoretical, this checkpoint also reproduced the historical
failure mode on the same clone: the tracking row was deleted (simulating an out-of-band apply),
and reconcile then correctly aborted — `unsupported ADD COLUMN type 'uuid'` — fail-closed exactly as
designed, refusing to backfill a tracking row it could not independently verify. This is a genuine,
pre-existing gap in the reconciler's allowlist (it has never covered `uuid`, `real`, `boolean`,
`bigint`, `smallint` or `integer` — only the handful of types `0009`/`0010` happened to add), not a
defect introduced by this migration, and it is **out of this checkpoint's scope to fix**: widening a
shared, safety-critical reconciliation tool is its own reviewed decision, not a side effect of
adding one column. It is recorded here rather than silently patched so the owner can decide whether
to broaden the allowlist pre-emptively or leave it to be widened the next time an out-of-band apply
actually needs it.

**Unchanged and reaffirmed:** ADR-024 (no backup system — this is exactly why the migration was
proven against a disposable clone first, never against `personalos` or the shared `personalos_test`),
ADR-050 (CHECK constraints only for project-controlled closed vocabularies — moot here, since this
column carries no CHECK at all), ADR-068 (Canvas data remains read-only and this column does not
change that — linking a task to an assignment records provenance on the task, it does not grant the
task any write path back into Canvas), ADR-056 (no AI, no embeddings — this is a plain relational
column with no model in its path). The Checkpoint 10.0 `tags`/`item_tags` safe-to-drop
classification is unaffected and remains an open owner decision, entirely separate from this
column (Checkpoint 10.5, 2026-09-17)
