# ADR-070 — Checkpoint 10.2: the Academic Intelligence Layer is a computed read model over the Canvas tables, structurally outside the AI lanes

**Status:** Locked

**Checkpoint 10.2 — Academic Intelligence Layer (2026-09-16, owner-approved).** Personal OS converts the Canvas data Checkpoint 10.1 already syncs into user-facing academic intelligence: a provider-agnostic academic model, deterministic Today cards, and a course browsing surface. It consumes the Canvas connection layer (ADR-068) unchanged. Three decisions were put to the owner before any code was written and are recorded here as taken. **1. THE "NORMALIZED ACADEMIC MODEL" IS A READ MODEL, NOT A SECOND STORE.** The brief asked for normalized Course / Assignment / Grade / Academic-Event entities; every field it named already exists on `canvas_courses`, `canvas_assignments`, `canvas_events` and `canvas_announcements` except the two ADR-068 §3 had excluded. Creating `academic_*` tables filled by a normalization job would have duplicated every row — the second source of truth `AGENTS.md` forbids and the same rule ADR-068 applies to due dates ("the assignment row is the one source of a due instant"). Instead `packages/schema/src/academic.ts` defines provider-agnostic `Academic*` shapes and `apps/api/src/read-models/academic.ts` computes them from the Canvas tables at request time — the "computed, never stored" idiom Today, Agenda, project next-action and stalled-project already use. Normalization is concrete, not nominal: Canvas's open vocabularies (`submission_state`, `enrollment_state`, `workflow_state`, `read_state`) map to closed, project-controlled enums with an honest `unknown` member, and every derived fact (`open`, `grade.percentage`, `grade.status`, a course's `status`, its open/overdue counts) is computed once, server-side, in pure `packages/core/src/academic/` helpers, never re-derived by a client. A future LMS adds a member to `AcademicSourceSchema` and a second collector, not a second schema. **No migration was needed for the model itself**; the only migration in this checkpoint is ADR-068a's two grade columns. **2. GRADES ARE STORED (ADR-068a); DESCRIPTION IS NOT.** Offered the choice of lifting neither, one or both of ADR-068 §3's exclusions, the owner chose grades only. `grading status` needed no new storage at all — it is the existing `submission_state` — and percentage is derived; only `score` and `grade` are new columns. **3. THE TODAY INTEGRATION IS A SEPARATE READ MODEL, DELIBERATELY NOT A SECTION OF `GET /today`.** `GET /academic/today?tz=` captures its own single `effectiveNow` and buckets with the same `packages/core` local-day-window primitives `/today` uses, so "overdue" (instant comparison) and "due today" (the client's local calendar day, overdue taking precedence) mean exactly the same instants on both models, and `due_this_week` is Today's own seven-day `upcoming` horizon. It is kept OUT of `TodayResponse` for one reason: both AI collectors — `apps/api/src/intelligence/today-context.ts` (Ask, Suggested Focus) and `apps/api/src/brief/collect-input.ts` (Daily Brief) — build from `buildTodayResponse` alone, so academic data cannot reach a model call by construction. This is the ADR-046 posture for Health ("displayed, never fed to the AI layer") applied to a second passive domain, and `ai-egress-guard.test.ts` pins the import boundary on top of the structural one. **The deterministic card set** (owner-approved default, the brief's own list having been truncated): Overdue · Due today · Due this week (each with an honest `total`, capped items and a "+N more" line), a recent-announcements section (seven-day lookback, unread first) and an upcoming-events section (seven-day horizon; the owner's account has no Canvas calendar events, so this section is structurally present and honestly empty), plus summary counts including Canvas's own `missing` flag, reported alongside `overdue_total` rather than reconciled with it. The Today card owns its own query and renders nothing at all when unconfigured or empty (the Health/Mail/Brief card posture), replacing — not duplicating — Checkpoint 10.1's standalone upcoming-assignments card; `GET /canvas-assignments/upcoming` is retained for the versionCode-22 client and marked superseded. **A course surface, not a sixth tab**: `/academic` (courses grouped by term with open/overdue/next-due) and `/academic/[id]` (assignments partitioned Overdue / Upcoming / No due date / Submitted & graded, then announcements and events) are stack screens reached from the Today card header and Settings, because a sixth tab does not fit the Rabbit R1's 480px tab bar. Every "open in Canvas" affordance stays behind the exact-origin check 10.1 verified live (`html_url` origin must equal the row's own `source_base_url` origin, fail closed to inert text). **One reliability debt closed in passing (Worker lane):** a Canvas `auth_failed` at the connection level now sets `canvas_connections.status = 'invalid_token'` — the CHECK-enforced member no production path ever wrote (recorded at 10.1C) — so a revoked PAT surfaces itself for reconnect through 10.1C's status-agnostic reactivation instead of failing quietly into `last_sync_error` forever; the credential triple is not nulled (that remains `disconnect`'s job). **Privacy and scope, reaffirmed:** no AI processing of academic data (structural + guard test), no new egress surface, no mutation of anything Canvas-side, no new table, no new queue, no new schedule, no new consent surface; Canvas content remains outside `GET /search` (ADR-065's privacy-argument rule). Unchanged: ADR-018, ADR-024, ADR-056, ADR-058 (no new alert producer), ADR-065, ADR-066/067 (Cloud Ask and Suggested Focus ship unchanged and cannot see academic data) (Checkpoint 10.2, 2026-09-16)
