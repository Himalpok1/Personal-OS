# ADR-082 — Checkpoint 10.9: approval, permission changes and agent management are bound to a paired device's bearer token (amends ADR-029)

**Status:** Locked

**Checkpoint 10.9 (2026-09-18, owner decision).** ADR-029 scoped device-token auth to
device/notification endpoints and left every other route Tailscale-perimeter-only; ADR-078 §5
recorded that "binding approval to a device token would be stronger than any existing write and
is deferred with the agent ADR." This is that ADR.

**1. THE FINDING — A CONFUSED DEPUTY, REAL AS SOON AS A SECOND PRINCIPAL EXISTS.** Under ADR-029
the only bearer-authenticated routes are `/devices/*`; `POST /actions/:id/approve`, `PATCH
/permissions/:permission` and every other write answer any caller the tailnet lets in. That was
an accepted posture while the only principal was the owner's own client (ADR-078 §5 named it
honestly). It stops being acceptable the moment an agent can hold a token and run on a tailnet
node: a process that can reach the API at all could **approve its own proposal**
(`POST /actions/:id/approve` with no credential), **grant itself a permission** (`PATCH
/permissions/tasks.write`), or **register itself an agent token** (`POST /agents`) — each a
perimeter-only route the discovery inventory listed. The Action Framework's "grants gate
requests, never execution" (ADR-078 §3) would still be true in code and false in practice,
because the deputy that executes would be taking orders from the thing it was meant to gate.
ADR-079 §4 makes the point concrete: Ray already runs on tailnet node `muse` with host access;
a product-level agent must never be able to close the approval loop from that position.

**2. THE ROUTE SET BOUND — EXACTLY THESE, THROUGH `deviceAuthPreHandler`.** The following now
run inside a Fastify sub-context whose `preHandler` is the existing `deviceAuthPreHandler`
(`apps/api/src/plugins/device-auth.ts` — Bearer → sha256 → `devices.token_hash`, live and
unrevoked, the ADR-028/029 mechanism unchanged):

| Route | Why it is the owner's tap and nothing else's |
|---|---|
| `POST /actions/:id/approve` | the one place an action executes (ADR-078 §4) |
| `POST /actions/:id/cancel` | the owner's withdrawal of a pending request |
| `PATCH /permissions/:permission` | the `app` principal's consent switch |
| `GET /permissions/agent`, `PATCH /permissions/agent/:permission` | the `agent` principal's consent switch (ADR-081 §4) |
| `POST /agents`, `GET /agents`, `GET /agents/:id`, `PATCH /agents/:id`, `POST /agents/:id/revoke`, `GET /agents/:id/activity` | minting, promoting, pausing and revoking an agent, and reading what it did (ADR-081 §3) |

A request to any of these without a bearer, with an unknown bearer, or with a revoked device's
bearer answers **401** before the handler runs; a live device behaves exactly as before. An
**agent** bearer (`posa_…`, ADR-081 §3) presented here is not a device token — the hook looks in
`devices`, not `agents` — and is refused the same way; Guard 8(d) additionally pins that
`routes/agents.ts` imports the device hook and never the agent hook, and that `routes/agent.ts`
never imports the device hook. Importing `plugins/device-auth.js` from the action routes does not
trip Guard 7's `OFF_LIMITS_DEVICES_IDENTIFIER`, which denies table access, not the hook.

**3. WHAT STAYS PERIMETER-ONLY, AND WHY.** `POST /actions` (proposing) stays as it was: a
proposal is inert until approved, and approval is now bound, so a perimeter caller that proposes
has gained nothing it could not already do by typing a task. Every read route stays as it was:
reads serve the trusted first-party client under ADR-029's posture, and this ADR is about the
routes that *close a loop*, not about narrowing reads. `GET /permissions` stays byte-identical
(a wire-freeze pin holds it): the deployed versionCode-33 client reads it unauthenticated on the
Action Center's Permissions tab and must keep rendering during the api→APK gap.

**4. THE CLIENT CHANGE.** `packages/api-client`'s `approveAction`, `cancelAction` and
`updatePermission`, and every function in its new `agents.ts`, take the paired device's bearer
as an argument; the mobile approve/cancel/permission/agent mutations pass
`useDeviceIdentity().token`. **The unpaired consequence is a state, not an error**: a session
that holds no device token — a fresh web tab, a reinstalled app before pairing — sees the
approval sheet render **"Pair this device to approve"** where Approve would be, the permission
and agent screens likewise, and is sent to pairing; nothing is greyed out silently and nothing
pretends the tap would work. Pairing itself is unchanged (ADR-028: a single-use code minted from
trusted CLI access).

**5. THE DEPLOYMENT CONSEQUENCE, STATED BEFORE IT HAPPENS.** The versionCode-33 APK approves
through the unauthenticated 10.8 call. From the moment the 10.9 api is recreated until the 10.9
APK is installed, that client's Approve and Cancel taps and its permission toggles answer 401 —
the Action Center still lists and reads, but cannot act. The deployment plan therefore performs
the api rollout and the `eas build --local` → `adb install -r` in **the same session**, and an
unpaired production web session must pair before it can approve. This is the ADR-082 analogue of
the 10.2 strict-schema gap, chosen with eyes open: the alternative — accepting an unauthenticated
approve for one more release — is the exact hole this ADR closes.

**6. THE RESIDUAL — AND THE HARD PRECONDITION FOR 10.10.** This ADR binds the routes that close
the agent loop. **Every other mutating route is still Tailscale-perimeter-only**: `POST /tasks`,
`PATCH /tasks/:id`, `POST /events`, the occurrence routes, the notes, projects and reviews routes,
the Canvas / Calendar / Gmail / Health connect and disconnect routes, `POST /memories` and its
siblings, the AI provider and task-route routes, `POST /capture`, `POST /transcribe` — the
inventory ADR-078 §2 drew from. An agent runtime on the tailnet does not need the gateway to write
a task if it can `POST /tasks` directly, and it does not need an approval if it can `POST
/ai/task-routes` itself. **Connecting an external agent to this tailnet is therefore NOT safe
until every mutating route is device-bound (or otherwise bound to the owner) — and the gateway
alone does not make it safe.** That closure is the hard precondition for Checkpoint 10.10 and for
issuing any production agent token, recorded here so it cannot be read as optional polish. It is
deliberately not done in 10.9: it touches every route file and the outbox, deserves its own
review, and would have doubled this checkpoint's blast radius during an api→APK gap.

**Unchanged and reaffirmed:** ADR-018 (Tailscale is still the perimeter; this ADR adds a second
factor for six route groups, it does not open anything), ADR-028 (pairing unchanged), ADR-029 for
every route not listed in §2 — including the honest consequence it already recorded, that a lost
device must also be removed from the tailnet for full revocation, ADR-041/043, ADR-078 §3–§4 (a
grant still gates requests, never execution; execution is still synchronous and single-use —
now under a verified owner tap), ADR-079 (the operator's host access is unaffected and outside
the product), ADR-081.
