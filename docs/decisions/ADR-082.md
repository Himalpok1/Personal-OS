# ADR-082 — Checkpoint 10.9: approval, permission changes and agent management are bound to a paired device's bearer token (amends ADR-029)

**Status:** Locked

**Checkpoint 10.9 (2026-09-18, owner decision).** ADR-029 scoped device-token auth to
device/notification endpoints and left every other route Tailscale-perimeter-only; ADR-078 §5
recorded that "binding approval to a device token would be stronger than any existing write and
is deferred with the agent ADR." This is that ADR. *(Lane D fills: the confused-deputy finding —
a process on the tailnet could approve its own proposal, grant itself a permission or register
itself an agent token; the exact route set bound — `POST /actions/:id/approve`,
`POST /actions/:id/cancel`, `PATCH /permissions/:permission`, `GET/PATCH /permissions/agent[/…]`,
every `/agents/*` owner route; what stays perimeter-only and why (proposing still needs approval;
reads are the trusted client's); the api-client token arguments; the mobile pairing prerequisite
("Pair this device to approve"); the deployment consequence — the versionCode-33 APK cannot
approve between the api deploy and the 10.9 APK install, an unpaired web session must pair; the
residual: every OTHER mutating route remains perimeter-only, so connecting an external agent on
the tailnet is NOT safe until that is closed — recorded as the hard precondition for 10.10.)*
