# ADR-080 — Checkpoint 10.8.5: a minimal backup — daily `pg_dump` + globals + a configuration bundle on the host, pulled to the owner's Mac daily; restore tested before the decision was recorded (amends ADR-024)

**Status:** Locked

**Checkpoint 10.8.5 (2026-09-18, owner-directed).** ADR-024 recorded *no backup system*:
persistent Docker storage is durability against container restarts, not a backup, and backup
infrastructure "may be added in a future phase only if explicitly requested". The 10.8.5 audit
found the request's reason on the host itself: production is one NVMe with ~1,500 correctable
PCIe errors a day (ADR-079 §7), shared with other stacks and a trusted agent that has already
deleted 163 GB by mistake. The owner's brief for this checkpoint asks, explicitly, for a minimal
backup plan covering the database, `.env`, the deployment configuration, release metadata and
the rollback artifacts. This ADR is that plan, and it supersedes ADR-024's "none" with the
smallest thing that is actually a backup: **restorable, tested, and on a second machine.**

**1. WHAT IS BACKED UP, AND WHERE.** `scripts/homelab/backup-personal-os.sh` (installed at
`~/personal-os-ops/`, `himallinux` crontab `30 3 * * *` local, no root) writes under
`~/personal-os-backups/` (mode 700):

| Artifact | How | Why it is enough |
|---|---|---|
| `db/personalos-<UTC>.dump` | `docker exec personal-os-postgres-1 pg_dump -Fc personalos` | custom format, compressed, `pg_restore`-able into any Postgres 17; 6.4 MB / 4 s at 10.8.5 |
| `db/globals-<UTC>.sql` | `pg_dumpall --globals-only` | the `posops_app`/`posops_migrator` roles (their passwords are in `.env`) |
| `config/<UTC>/env` (0600) | copy of `/home/himallinux/personal-os/.env` | every credential and key the service needs; without it a restored database is unreadable (`CREDENTIALS_ENCRYPTION_KEY`) |
| `config/<UTC>/docker-compose*.yml`, `tailscale-serve.txt`, `crontab.txt`, `authorized_keys.txt` | copies from the serving release directory and the host | the deployment configuration, the HTTPS routes, the host automation, the public keys |
| `config/<UTC>/release.txt`, `docker-images.txt`, `docker-containers.txt`, `image-store.txt` | inventories | release provenance (which release directory and image serves each container, the migration watermark), so a rebuild knows what to rebuild |
| `~/personal-os-images/<label>/` | ADR-079 §2 (`save-release-images.sh`) | the rollback and serving images as tarballs — release artifacts, kept beside the backups |

Every file has a sha256 sidecar; the dump is verified with `pg_restore --list` before the run
reports success; retention keeps the newest **14 days**. `latest` symlinks the newest bundle.

**2. THE OFF-HOST COPY IS WHAT MAKES IT A BACKUP.** Everything above sits on the same disk as
the data. `scripts/homelab/pull-backup.sh` runs on the owner's Mac mini (a launchd user agent,
`com.personal-os.pull-backup`, daily 09:30 local; installed with `--install-launchd`) and
`rsync --delete`s `personal-os-backups/` and `personal-os-images/` over SSH with the deployment
key into `~/PersonalOS-Backups/host/` (mode 700; ~1.3 GB, dominated by the image tarballs). It
never writes to the host. The Mac's disk is FileVault-encrypted; the copy is not separately
encrypted (the ADR-024-era SOPS/age discipline is not applied here — one machine, one owner, a
local disk). The repository itself is on the private GitHub remote and is not copied.

**3. RESTORE IS A DOCUMENTED, TESTED PROCEDURE.** Tested at this checkpoint on the host: the
first dump restored into a scratch database (`pg_restore --no-owner`), every table's row count
compared equal to production (tasks 27, events 110, occurrences 227, canvas_assignments 355,
action_requests 11, …), all 25 migrations present, scratch dropped. The procedure, in
`docs/HOMELAB-RUNBOOK.md` §5:

1. Host rebuilt or volume lost: install Docker, restore `.env` from the bundle to
   `/home/himallinux/personal-os/.env`, ship the release directory (`git archive` of the tagged
   commit, or the copied one), `docker load` the image tarballs (or build).
2. `docker compose … up -d postgres` alone; wait healthy; apply the globals (`psql -f
   globals-<ts>.sql`) — the init scripts create the roles on a fresh volume, the globals cover a
   volume that lost them.
3. `pg_restore -U postgres -d personalos --no-owner --clean --if-exists personalos-<ts>.dump`
   (into the empty database the init created).
4. Bring up `api`, `worker`, `web`; `tailscale serve` from `tailscale-serve.txt`; the crontab
   from `crontab.txt`; `scripts/homelab/preflight.sh`.

The Rabbit R1's device rows and outbox are in the dump; its pairing survives.

**4. WHAT THIS IS NOT.** Not point-in-time recovery (up to 24 h of writes can be lost — the
capture pipeline's outbox on the device re-sends anything not yet acknowledged, and Canvas /
Gmail / Health / Calendar data re-syncs from its provider). Not encrypted at rest beyond
FileVault. Not a backup of the other home-lab stacks on the host (Immich, the dev-ops volumes,
Ray's projects) — those are the owner's, outside Personal OS. Not a replacement for the
per-release directories and git tags as the rollback source (ADR-079 §2).

**5. WHAT THE WATCHDOG ENFORCES.** `check-host.sh` turns YELLOW when no dump exists or the
newest is older than 36 hours, and reports the dump count and store size in every heartbeat.

**Amends ADR-024.** "No backup system" no longer holds; the sentence *persistent Docker storage
is not a backup* still does, and is now the reason for this ADR. ADR-018 unchanged (the pull
runs over the tailnet with the existing deployment key; nothing new listens). ADR-079 §2
unchanged (image tarballs are release artifacts; this ADR only copies them off-host).
