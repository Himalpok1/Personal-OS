# ADR-073 — Checkpoint 10.4: a single, hysteresis-gated Canvas invalid-token alert, amending ADR-068 §6's "no alert" stance

**Status:** Locked

**Checkpoint 10.4, Lane 4 (2026-09-16, owner-approved).** On 2026-09-16 in production a real Canvas connection silently flipped to `invalid_token` (a dead PAT), and the owner only discovered it because the academic UI went blank. Every OTHER integration (Gmail, Health, Calendar) fires a deduped push alert the instant its connection breaks; Canvas was the only one that did not — `apps/worker/src/canvas/orchestrate.ts`'s own header comment said so explicitly: a dead PAT flips the row to `invalid_token`, but "unlike mail's `needs_reauth`, enqueues no alert — the Settings screen's own status rendering is the surface, and an alert producer would need its own occurrence-scoped dedupe key under ADR-058 first." This closes that gap, and closes it together with an already-recorded piece of Checkpoint 10.2 debt in the same motion: "a connection-level non-rate-limit 403 classifies as `auth_failed` and flips `invalid_token` on a single run (no hysteresis)... a two-consecutive-runs hysteresis is recorded below, not built."

**This is a narrow, single-condition addition, not a Canvas observability subsystem** — the same restraint ADR-068 §6 already named and the same restraint `apps/worker/src/mail/alerts.ts`'s own header comment states for Gmail ("this adds exactly one alertable condition… because that is the only mail state a user can DO something about"). Canvas gets exactly one alertable condition too: the connection has entered `invalid_token`. Every other Canvas failure class — `rate_limited`, `provider_error`, `blocked_url`, a per-course `auth_failed` (contained inside the course loop and never reaching the connection-level catch block at all) — stays exactly as unalerted as before, because each is either transient (the hourly cron tick is already the retry), contained to one course, or not actionable by the owner.

**The flip itself now requires TWO CONSECUTIVE connection-level `auth_failed` failures, not one.** Before this checkpoint, `runCanvasConnectionSync`'s catch block called `markConnectionInvalidToken` unconditionally on the very first connection-level `auth_failed` (a 401, or a non-rate-limit 403, on `listActiveCourses` — the one request that carries no course id, meaning the PAT itself, not one course's enrollment, was rejected). A single transient Canvas permission blip was therefore indistinguishable from a genuinely dead token, and forced the owner to re-paste a PAT that may never have actually been revoked. `isSecondConsecutiveAuthFailure` (orchestrate.ts) now gates the flip: it reads the `canvas_sync_runs` row immediately preceding the one that just failed (most recent by `started_at`, excluding the just-closed run by id) and only proceeds to `markConnectionInvalidToken` — and, immediately after, the new alert — if that prior row was ALSO `status = 'failed'` with `failure_class = 'auth_failed'`. A first occurrence, a prior success, or a prior failure of a *different* class all fall through to the existing `recordConnectionError` path instead: the connection stays `active`, `last_sync_error`/`last_sync_error_at` record the attempt, and the next cron tick retries — which is exactly what makes two-in-a-row possible to observe naturally under an unattended cron in the first place, since the connection is never removed from `enqueueCanvasSyncForAllActiveConnections`'s `status = 'active'` selection after only one failure.

**The alert producer, `enqueueCanvasInvalidTokenAlert` (`apps/worker/src/canvas/alerts.ts`), is Canvas's copy of the same contract every other integration alert already follows under ADR-058.** Dedupe key: `canvas-invalid-token:<connectionId>:<last_sync_error_at ISO>`, re-read from the connection row at send time. `last_sync_error_at` is NOT episode-exact by its writer set alone — `recordConnectionError`'s non-fatal path also writes it, including on the first, absorbed failure of a streak — but it is episode-STABLE for the identical, weaker reason Gmail's own file documents its column is: once a connection leaves `active` status, `enqueueCanvasSyncForAllActiveConnections` selects `status = 'active'` only, so no further sync pass of any kind touches `last_sync_error_at` again until the owner reconnects through the Checkpoint 10.1C path (which replaces the credential and clears the error columns atomically, ending the episode). The function re-selects the connection fresh and no-ops if `status !== 'invalid_token'` — the same "reconnected or disconnected in between" guard Gmail's producer uses — so a race between the flip and a concurrent reconnect or disconnect never mints a key for an episode that never took. The alert body is a closed, static taxonomy of one member (`{ invalid_token: { title: "Canvas needs reconnecting", body: "Assignment sync has stopped. Reconnect it in Settings." } }`); like every other alert in the system it carries no identifier — no institution name, no `canvas_base_url`, no course or assignment content — matching ADR-054's discipline that mail already follows and that Canvas's own notification-facing surfaces (ADR-068's Today card, `source-link.tsx`'s same-origin link) have never violated. Eligible devices are selected exactly as every other alert producer selects them (`notify_alerts = true`, `notifications_enabled = true`, `revoked_at is null`), dispatched through the existing `NOTIFICATIONS_DISPATCH_QUEUE` with `category: "alert"` and `data: { canvasConnectionId: connectionId }` only.

**No migration, no schema change.** `canvas_connections.status`'s existing CHECK vocabulary (`active`, `disconnected`, `invalid_token`) and `canvas_sync_runs`'s existing `status`/`failure_class` columns already carry everything the hysteresis check and the alert discriminator need — this checkpoint is read-and-decide logic over rows the schema has held since ADR-068 (migration `0020`) and the worker's own writes since Checkpoint 10.2. `CanvasSyncDeps.boss`, reserved since Checkpoint 10.1 "the same way `MailSyncDeps.boss` was in 7.3, in case a future checkpoint adds an alert producer here," is genuinely used for the first time. **Unchanged and reaffirmed:** ADR-018 (no new ingress — the alert is outbound push through the existing dispatch queue, not a new listener), ADR-024, ADR-056 (no AI, no embeddings — this producer is deterministic status-column logic, not a model call, and sits outside every AI lane's import surface exactly as the rest of `apps/worker/src/canvas/` does), ADR-058 (the dedupe-key contract this checkpoint implements for Canvas rather than amends), ADR-068 (auth remains PAT-only, read-only; this is the one narrow amendment to §6's "no new egress surface" stance, adding exactly the alert §6 itself anticipated might one day need its own ADR) (Checkpoint 10.4, 2026-09-16)
