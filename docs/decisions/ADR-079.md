# ADR-079 — Checkpoint 10.8.5: the production host is a shared home-lab box — image rollback artifacts are saved, not merely tagged; the deployment key lives in a root-owned file; an autonomous agent never holds an unrestricted key to the production host

**Status:** Locked

**Checkpoint 10.8.5 (2026-09-18, owner-directed).** During the Checkpoint 10.8 deployment every
Docker image not held by a running container was deleted on the production host (~163 GB: every
`rollback-pre-10.x` tag, every earlier release image, the build cache), and the evening before the
deployment SSH key had been dropped from `~/.ssh/authorized_keys`. The owner's brief for 10.8.5:
identify the source before changing anything, then protect the artifacts, restore reliable
deployment access, add visibility, and only then prepare the host for future phases. This ADR
records what the audit found and the rules it leaves behind.

**1. ROOT CAUSE — BOTH INCIDENTS ARE THE SAME ACTOR: THE OWNER'S OWN AI AGENT WITH AN UNRESTRICTED
KEY.** Since 2026-09-17 the host also runs a home-lab stack (`~/docker/dev-ops`: Watchtower,
Dozzle, Uptime Kuma, Glance, ntfy, it-tools; plus code-server, a Claude Desktop container, Immich,
a `ray-dashboard` kiosk page and an "agent meetup" board). The `ray-dashboard` README and
`tools/collect_apps.py` name the operator: **Ray, the owner's AI agent**, running as user `hatch`
on tailnet node `muse` (100.84.166.123), which holds an SSH key (`SHA256:vA8oSk…`, comment
`hatch`) for `himallinux` — a member of `docker`, i.e. root-equivalent — with **no `command=`,
no `restrict`, no source restriction**. It logs in every three minutes for `docker ps`/`docker
stats` (the dashboard poll) and, when asked, performs host setup through the same key.

- *The prune.* Docker's event buffer holds 256 events (seconds, on this host) and `dockerd` does
  not journal image removals, so the deletion left no Docker trace. `sysstat` did record it:
  `sar -b` shows the 10-minute sample **01:30–01:40 CDT (06:30–06:40Z) at 1,686 tps / 15.9 MB/s
  reads** — a mass unlink — between two idle samples (6 and 46 tps). The only SSH session open
  across that interval that was not a one-second poll was **Ray's, pid 3674631, 01:29:18–01:40:08
  CDT**; the same burst of Ray sessions created `~/serve-landing` (01:23) and started `code-server`
  (01:44), and the disk was at 87 %. The stopped `hello-world` container from Aug 15 survived, so
  the verb was `docker image prune -a` (plus a builder prune), not `docker system prune`. A
  non-interactive SSH command writes no bash history and needs no `sudo`, which is why nothing
  else recorded it. The owner's interactive session (01:01–01:38 CDT) overlaps the window and left
  three `ssh`-diagnostic commands in history; it is the residual alternative, and Ray's own
  transcript on `muse` for 06:29–06:40Z is the one artifact that would make the attribution
  certain — an owner action.
- *The key.* The last deploy-key login before the rewrite was 21:58:03 CDT on 2026-09-17; `.ssh`,
  `.local` and `.venvs` were all modified at 22:02 during a burst of ~40 Ray sessions
  (21:50–22:02); no deploy-key login succeeded again until the owner ran `ssh-copy-id` at 01:01 on
  09-18 (password auth was still enabled — the recovery path). An agent setup step rewrote the
  file instead of appending to it.

**2. IMAGE TAGS ARE EPHEMERAL ON A SHARED HOST; THE ROLLBACK ARTIFACT IS SAVED, REFERENCED AND
BOUNDED.** Docker has no protected-image flag: `image prune -a` removes every image no container
references, and `system prune -a` removes stopped containers first. Three layers, cheapest first,
all in `scripts/homelab/save-release-images.sh` (installed at `~/personal-os-ops/` on the host):

- **A saved tarball per image** (`docker save | gzip`, sha256, manifest) under
  `~/personal-os-images/<label>/` — immune to every prune verb; ~640 MB per three-image set;
  `docker load` restores in seconds where a rebuild from the release directory takes minutes.
- **A stopped "keeper" container per saved image** (`docker create … true`, label
  `io.personal-os.keeper=true`) — the reference that makes `image prune -a` skip the image.
  Verified by Docker's own accounting: image *Reclaimable* fell from 1.17 GB to 88 KB the moment
  the keepers existed.
- **`LABEL io.personal-os.protected="true"` on every Personal OS image** (the three Dockerfiles'
  runtime stages) — a cooperative marker so that any cleanup can exclude them
  (`--filter "label!=io.personal-os.protected=true"`). A marker, not an enforcement.
- **Retention is explicit: the newest two labels** (current release + previous) are kept; older
  tarballs, keepers and `:<label>` tags are retired by the same script. That bounds the growth
  that reached 163 GB (every release's images kept forever, plus an unbounded build cache).
  `:latest`, non-Personal-OS images, running containers and volumes are never touched.

The durable rollback source is unchanged and reaffirmed: the per-release directory
(`/home/himallinux/personal-os-<checkpoint>-release`, a `git archive`) plus the pushed
`rollback-pre-<checkpoint>` git tag. The tarball is the fast path; the release directory is the
proof.

**3. THE DEPLOYMENT KEY LIVES IN A FILE THE LOGIN USER CANNOT REWRITE.** `sshd` reads
`/etc/ssh/authorized_keys.d/%u` (root-owned, 0644) in addition to `~/.ssh/authorized_keys`
(`scripts/homelab/harden-ssh.sh`, a root step the owner runs). Every agent, script or human
holding a key for `himallinux` can still rewrite the user file; none of them can remove the
deployment key. Password authentication stays on until the root-owned file has been proven to log
in from the Mac; the script offers `--disable-password-auth` for that moment, and `sshd` on
`0.0.0.0:22` with password auth is recorded as a remaining risk until then.

**4. AN AUTONOMOUS AGENT NEVER HOLDS AN UNRESTRICTED KEY TO THE PRODUCTION HOST.** The always-on
poll key is bound to a forced command (`scripts/homelab/ray-poll-wrapper.sh`: `restrict,command=…`)
that allows exactly the read-only status commands the dashboard needs and logs a counts-only line
for every allowed and refused call. Host administration by an agent, when the owner wants it, uses
a **separate key the owner enables on purpose and can revoke**, never the poll key; and any
cleanup an agent performs excludes the protected label (§2). Installing the forced command on
Ray's existing key changes what the owner's other agent can do, so it is an **owner decision** —
prepared and documented, applied only on the owner's word. Docker-socket mounts on the host are
allowlisted by the watchdog (§5): Watchtower read-write (label-gated, weekly, never a Personal OS
container), Dozzle read-only; a new read-write mount is a YELLOW.

**5. THE HOST WATCHES ITSELF WITH WHAT IS ALREADY THERE.** `scripts/homelab/check-host.sh` runs
from the `himallinux` crontab every 30 minutes (no root, no new service): root disk usage (80/90),
the four Personal OS containers, `GET /health` and worker staleness, one `rollback-pre-*` tag per
service, a complete saved image set, the deployment key's fingerprint in `authorized_keys`,
read-write socket mounts outside the allowlist, the reboot-required flag. It posts to the **ntfy**
topic `personal-os-ops` already running on the host only when the set of problems changes, plus
one low-priority heartbeat a day so a dead watchdog is visible. `--report` is the deployment
preflight (`scripts/homelab/preflight.sh`, which first proves a BatchMode login) and the
post-reboot validation; it adds `tailscale serve`, the public HTTPS `/health` and the day's NVMe
AER count. Personal OS's own monitoring (ADR-055) is not widened: this is host telemetry outside
the product, and every line is a count, a status token or a name.

**6. OS UPDATES FOLLOW THE ROOT CAUSE, AND THE REBOOT IS AN EXPLICIT OWNER COMMAND.** With the
cause understood, `scripts/homelab/apply-os-updates.sh` applies the pending set (76 packages at
audit, including `docker-ce`/`containerd.io`, whose upgrade restarts every container — a ~30 s
outage with live-restore off) and the kernel/libc reboot is a separate command; `preflight.sh`
validates afterwards. Neither runs without the owner's password.

**7. ONE HARDWARE FINDING IS RECORDED, NOT FIXED.** The kernel has logged **38,098 correctable
PCIe AER errors on the NVMe link** since boot (Aug 29; ~1,500/day). Correctable errors do not
corrupt data, but the rate is a signal on the only disk of a host that, by ADR-024, has **no
backup**. The watchdog reports the daily count; `nvme smart-log`, a reseat or `pcie_aspm=off` are
owner actions after the reboot. ADR-024 is not reopened here — but this is the sharpest reason to
reconsider it.

**Unchanged and reaffirmed.** ADR-018 (Tailscale-only; every home-lab service except the kiosk
page binds the tailnet IP; nothing new is public), ADR-024 (no backup system — the saved image
tarballs are release artifacts, not data backups), ADR-029, ADR-055 (monitoring ownership;
the host watchdog is outside the product), ADR-058 (no new alert producer inside Personal OS),
the frozen deployment order of Checkpoint 5.7 (extended, not replaced: a preflight before step 1
and an image save after step 6).
