# ADR-081 — Checkpoint 10.9: the Agent Gateway — a versioned read-tool contract bound for the first time, an agent identity with trust levels, per-principal read permissions, budgeted and audited tool calls, agent proposals through the Action Framework, and Guard 8 (migration 0025)

**Status:** Locked

**Checkpoint 10.9 (2026-09-18, owner-directed; four scope decisions owner-approved the same
day).** The brief moves Personal OS from "can safely prepare and execute controlled actions"
(ADR-078) to "a future agent can operate through Personal OS without bypassing its privacy,
permission, memory, context, action and audit boundaries" — and forbids selecting or integrating
any agent runtime (OpenClaw, Hermes, LangGraph or other), any autonomous loop, planning engine,
vector store, knowledge graph, LLM memory or generic tool registry. The guiding principle:
*Personal OS owns identity, context, memory, permissions, tools, actions, approvals and
auditability; the agent is replaceable.* A three-lane read-only discovery preceded any code; its
findings are §1. The four decisions the discovery could not make alone were put to the owner and
decided: a migration (§3); device-bound approval now (ADR-082); the five ADR-066 tools **plus**
`get_academic_context` under its own OFF-by-default permission (ADR-070b); an Agent Center on
mobile with the existing approval sheet, no chatbot (§9).

**1. WHAT THE DISCOVERY ESTABLISHED.** (i) The API had no principal abstraction: device-token auth
lived only on `/devices/*` (ADR-029) and `principal` was the literal `"app"` at eight sites in
`apps/api/src/actions/service.ts`; nothing recorded a *read*. Identity and read-audit therefore
need a migration; the write side (`action_requests`, `permission_grants`, the `agent` CHECK
member) does not. (ii) Every action/permission wire shape the deployed versionCode-33 client
parses is `.strict()`, so agent attribution cannot be a new key (the 10.2 lesson) — it rides on
the existing `principal: "agent"` and `source_ref`, plus a separate agent read model. (iii) Guards
4–7 walk literal directory lists; a new `apps/api/src/agent/` directory was invisible to all of
them. (iv) Every owner route being Tailscale-perimeter-only meant a tailnet process could call
`POST /actions/:id/approve` itself — the confused deputy ADR-078 §5 deferred to "the agent ADR".
(v) `buildTodayContext` requires a `WeakSet`-branded grant minted only inside a live request by
`authorizeCloudAsk`, which needs the `ask` consent row; Guard 3 forbids every forging cast.
(vi) `READ_TOOL_MAX_CALLS_PER_REQUEST` / `READ_TOOL_MAX_CHARS_PER_REQUEST` had zero enforcement
sites; `get_calendar_context` / `get_task_context` had input schemas only.

**2. THE ARCHITECTURE: A BOUNDARY, NOT A LANE.** The gateway is the surface an agent *speaks to*;
it is not a place where a model runs. Its whole shape is two route prefixes that never share a
guard, and one direction of data flow:

```
Owner (paired device — ADR-082)              Agent (posa_ bearer — /agent/* only)
  POST  /agents               → token, once     GET  /agent/manifest              the versioned contract
  PATCH /agents/:id           trust level       POST /agent/tools/:tool           read: permission → trust → budget → audit
  POST  /agents/:id/revoke    revoked_at        POST /agent/actions               PROPOSE only (principal = agent)
  GET   /agents/:id/activity  what it did       GET  /agent/actions[/:id]         its own rows only
  GET/PATCH /permissions/agent[/:p]             POST /agent/actions/:id/cancel    its own pending rows only
  POST  /actions/:id/approve  ← the ONLY approve route, device-bound; no /agent/* route approves

        Personal OS DB → read models → intelligence builders ─┐
                                                              ├─► gateway ─► an authenticated principal
        action registry ← createActionRequest(attribution) ◄──┘             the OWNER registered
```

Four rules follow, each with an enforcement site. *Reads are tools, writes are actions* (ADR-078
§1): an agent CALLS one of the six `READ_TOOL_NAMES` (`^(search|get)_`, Guard 4) and may only
REQUEST one of the six `ACTION_IDS`; the owner approves in the Action Center. *No agent route can
approve*: `routes/agent.ts` carries no `/approve` path, imports `agentAuthPreHandler` and never
`deviceAuthPreHandler`, and the reverse holds for `routes/devices.ts` — Guard 8(d) pins all three.
*The gateway returns data to a registered principal, never to a model*: the six-member
`generateText` call-site set Guard 1 pins is byte-unchanged, nothing under `agent/**` may import
`ai`, a provider package, or the model-calling half of any lane (`ask/generate|prompt|
select-context`, `focus/`, `brief/` — Guard 8(a)), and no pg-boss token may appear (there is no
queued, scheduled or retried agent work — ADR-041/066/067's synchronous rule holds). *Nothing
reaches back into it*: no AI lane, AI route file, other read model or worker file may import an
agent module or name an agent table (Guard 8(b)), so a model's output can never become an agent's
proposal and a job can never call a tool on an agent's behalf.

The trust model this fixes, once, so no later checkpoint re-derives it:

| Level | Name | Who | May | Enforced by |
|---|---|---|---|---|
| 0 | `none` | a registered, paused agent | nothing — every `/agent/*` call after `/manifest` is refused `trust_insufficient` and audited | `authorizeAgentRead` returns `null` for `none`; the proposal path checks `trustLevelAtLeast(level, "propose")` |
| 1 | `read` | an agent the owner lets read | call the read tools whose permission the owner granted | the same two checks |
| 2 | `propose` | an agent the owner lets suggest | read, and `POST /agent/actions` — a `pending` row the owner approves or cancels | `createActionRequest` under `principal: "agent"` + the `tasks.write` / `calendar.write` grant for the `agent` principal |
| 3 | *operator* | Ray on the host (ADR-079 §4) | anything the host allows, under the audit shell | **outside the product.** Not a `trust_level` member, no CHECK member, no code path: nothing in Personal OS ever executes without the owner's tap, so the product cannot express a level that would |

**3. IDENTITY (MIGRATION 0025, LEVEL 25 → 26).** `packages/db/drizzle/0025_agent_gateway.sql`
adds two tables and widens one. **`agents`** — `name` (CHECK `char_length between 1 and 60`,
`AGENT_NAME_MAX_CHARS`), `trust_level` (CHECK `none|read|propose`, DB default `none`: a freshly
inserted row that forgets the column is paused, never able), `token_hash` (UNIQUE; the sha256 hex
of a `posa_` + base64url(32 random bytes) bearer generated by `packages/core/src/agent-auth.ts` and
returned to the owner exactly once in the `POST /agents` response — the `devices.token_hash` idiom
of ADR-028, with a visible prefix so an agent token is recognisable by eye in a terminal and by a
secret scanner in a log, which a bare base64url string is not), `disclosure_version` (WHICH
registration disclosure the owner agreed to — `AGENT_DISCLOSURE_VERSION`, the `permission_grants`
idiom, so a widened disclosure can be shown as needing re-consent), `created_at`/`updated_at`,
`last_seen_at` (diagnostic, bumped by the auth hook, **not** a heartbeat — exactly as
`devices.last_seen_at` is not), `revoked_at` (revocation is a timestamp, never a DELETE, so every
audit row that references the agent keeps its attribution; a revoked token authenticates nothing).
**`agent_tool_calls`** — one row per tool call *including refusals*: `agent_id` (FK, no cascade),
`correlation_id`, `tool_name` (CHECKed against the six names — a seventh tool is a migration, on
purpose), `status` (CHECK `completed|refused|failed`), `error_class` (token-shaped, paired with
status by CHECK: `completed ⟺ error_class is null`), `chars_returned` (≥ 0 by CHECK; the length of
the serialized output, what the char budget is counted from), `duration_ms`, `called_at`; indexed
on `(agent_id, called_at)` and `correlation_id`. **`action_requests`** gains `agent_id` (FK to
`agents`, no cascade) and `correlation_id`, the pair CHECK `(principal = 'agent') = (agent_id is
not null)` — an `agent` row without an agent, or an `app` row claiming one, is impossible — and an
index on `(agent_id, requested_at)`. Its `source` CHECK is dropped and re-added with `agent` (the
`0009` precedent). `packages/db/test/agent-constraints.test.ts` proves every CHECK, the UNIQUE
hash, the FK `23503`, the pair CHECK and the runtime role's DML through default privileges against
a real Postgres.

*The identity model, stated as what is and is not stored.* An agent is `agents.id`. A unit of
work is `correlation_id`, an agent-supplied uuid on every tool call and proposal — the key every
budget is counted against and the key the activity screen groups on. A proposal is the
`action_requests` row itself (`request_id` in the brief's vocabulary); a read is an
`agent_tool_calls` row. Timestamps are per state, as ADR-078 §4 already does. **Not stored:**
the prompt (there is none — the gateway never sees one), the tool input and the tool output (the
row records THAT a read happened and how many characters left, never what), any transcript, any
model name. The stored payload of a proposal is the action's validated `input` frozen as jsonb,
bounded by the action's own `.strict()` schema exactly as an owner's proposal is.

*The session model — decided, not deferred.* There are **no persisted sessions.** Every
`/agent/*` request is authenticated from scratch by the bearer; `correlation_id` is the only
grouping the server knows and it is the agent's to choose; `client_uuid` on a proposal gives a
retried `POST /agent/actions` the existing row (the `POST /events` idiom); Fastify's `request.id`
ties a call's log lines together and is what `authorizeAgentRead` binds the grant to. A session
table would be a place to keep conversation state, and conversation state is the runtime's, not
Personal OS's — the runtime is replaceable precisely because the gateway keeps nothing of it.

*The `source: 'agent'` widening — the one deliberate change to a frozen 10.8 enum, and why it is
safe.* `ACTION_SOURCES` and the `action_requests_source` CHECK gain `agent`. The deployed
versionCode-33 client parses `source` through a strict enum, so a `source: "agent"` row in its list
would blank the Action Center during the api→APK gap. It cannot happen: a row with that source can
only be written by the gateway for a registered agent, and an agent can only be registered from
`POST /agents`, a device-bound route the versionCode-33 client has no code to call. The first
`agent` row can therefore exist only after a 10.9 client is in use — and that includes the
production *web* client, which understands the source the moment `web` is recreated: the window in
which the Rabbit's versionCode-33 APK could meet an `agent` row is the same api→APK window ADR-082
§5 already records (the owner registering an agent from the web client and that agent proposing
before the APK is installed). Both close at the same install. **No new key is added to any
strict 10.8 schema** (`ActionRequestItemSchema`, `PermissionGrantItemSchema`,
`PermissionsResponseSchema`, `PermissionUpdateSchema`, `ActionRequestSchema`); `source_ref =
agent.id` is the projection of `agent_id` onto the wire shape the client already parses, and
agent-specific data travels on its own read model (`AgentSchema`, `AgentActivityItemSchema`,
`AgentPermissionGrantItemSchema` — the last is deliberately NOT `PermissionGrantItemSchema`, whose
`tasks|calendar` category and `action_ids` could never carry a read permission). Neither agent table
joins `GET /export`: they are the audit class, like `notification_dispatch_log` and the
`*_sync_runs` tables, not user-authored core (ADR-059). Rollback is image-only (§11).

**4. TRUST LEVELS AND PER-PRINCIPAL PERMISSIONS.** Two orthogonal axes, deliberately. *Trust
level* is per agent (`agents.trust_level`, §2's table): the owner's answer to "how far may this
one go". *Permissions* stay per principal in `permission_grants` under `principal = 'agent'`: the
owner's answer to "what may agents, as a class, touch". A per-agent permission matrix was
considered and rejected — it would multiply the consent surface by the number of agents while
the reserved `agent` CHECK member and the lazy-default read model already model the class; a
second agent inherits the first's grants and its own trust level, and the owner reasons about one
grant list. `READ_PERMISSIONS = context.read | items.read | academic.read` is a **sibling** of the
wire-frozen `ACTION_PERMISSIONS` (which stays exactly `tasks.write | calendar.write`, parsed by
the deployed client); `AGENT_PERMISSIONS` is their union and is what `PATCH /permissions/agent/:p`
accepts. `context.read` covers the four id/title-level tools; `items.read` is separate because
`get_item_context` carries a body; `academic.read` is separate because academic data is otherwise
structurally outside every AI-adjacent surface (ADR-070, amended by ADR-070b for this one gate).
**Every agent grant ships OFF**: `grantIsLive("agent", undefined)` is already `false` in the 10.8
read model, the migration inserts nothing, and no lazy default exists for the `agent` principal —
a grant is a row the owner created from a paired device. **`memory.read` is reserved and not
bound**: `RESERVED_PERMISSION_NAMES` names it so a test can prove it parse-fails; binding it needs
its own ADR, a new disclosure vintage and a Guard 6 amendment (ADR-077 §6). There will never be a
read member for health (ADR-046), mail (ADR-054), credentials or AI config, and the gateway cannot
name their tables (Guard 8(a)). Grants gate *requests*, never execution (ADR-078 §3): a `propose`
agent with `tasks.write` may create a `pending` row; only the owner's device-bound tap runs it.

Two `"app"`-literal gaps the discovery found in `actions/service.ts` are closed because two
principals now exist. **`runHandler` re-checks the grant under the row's own principal** at
approval time (it checked the literal `"app"`), so an agent's pending row is refused at the
owner's tap if the agent grant was revoked after the proposal — the grant is evaluated at both
ends, as ADR-078 §4 intended. **`setPermissionGrant`'s pending-cancel is principal-scoped**: a
revoke of `tasks.write` for `app` cancels the owner's own pending task requests and leaves an
agent's untouched, and vice versa (previously it would have cancelled both); a read permission's
revoke cancels nothing, there being nothing pending to cancel. Both are pinned by route tests.

**5. THE READ-TOOL CONTRACT, BOUND.** `READ_TOOL_NAMES` gains `get_academic_context`
(ADR-070b), and every one of the six is implemented and dispatched by `POST /agent/tools/:tool`
for the first time. `READ_TOOL_OUTPUT_SCHEMAS satisfies Record<ReadToolName, ZodTypeAny>` makes
the output side as closed as the input side: every output is `.strict()`; every list is capped
with an honest `total` (calendar ≤ 100 items with `truncated`, task occurrences ≤ 10, academic
assignments ≤ 40 and courses ≤ 20); every title is bounded to `TODAY_CONTEXT_TITLE_MAX_CHARS`
(120) and every location to 80 through the same `stripUnsummarizableCharacters` +
`truncateAtWordBoundary` pair `today-context.ts` uses; and **no output carries a body, a
description or a rule** except `get_item_context`, whose bounded body is exactly why it sits
behind its own `items.read`. `GetCalendarContextOutputSchema` has no description field at all (an
external event's description is attacker-authored, ADR-054/066) and reports a recurring
instance's OWN instant, never the series template's (the 10.6 briefing defect class);
`GetTaskContextOutputSchema` carries `recurring: boolean` and `canvas_linked: boolean` — that a
rule or an ADR-074 link exists, never the rule text or the assignment.

*The context contract.* The agent **asks for specific context; nothing is pushed.** There is no
"here is everything relevant" call: a Today overview is `get_today_context {tz}`, a window is
`get_calendar_context {tz, from, to}` with a span the input schema refuses above 14 days, one
task is `get_task_context {id}`, one body is `get_item_context {type, id}`, and search is bounded
to ≤ 10 per type. **Ids ARE carried** (unlike the prompt-facing, ordinal-`ref` `TodayContext`),
because a principal that may PROPOSE must be able to name a target — and the gateway hands these
to an authenticated principal the owner registered, not to a model. `get_today_context` is
`buildTodayContext(ctx).context` — literally the function the Ask lane calls, unchanged, as
ADR-066 §4 designed — and the two new builders `buildCalendarContext` / `buildTaskContext`
(`apps/api/src/intelligence/`) obey its rules: `assertGrant(ctx.grant)` is the first statement,
reads go only through a read model (`read-models/calendar-context.ts`, `read-models/task-context.ts`
— the latter listed in Guard 2's `EXPECTED_BODY_READERS` because it selects from `tasks`), and
imports stay inside Guard 4's allowlist.

*The second and only other grant-mint site.* `authorizeAgentRead(request, subject,
permissionGranted)` in `apps/api/src/ask/authorize.ts` takes row FIELDS (`id`, `trustLevel`,
`revokedAt`) rather than an agent import, so the ask module stays free of agent modules; it
returns `null` — having read nothing — for a revoked agent, a `none` agent, an ungranted
permission or a missing live `FastifyRequest`, and otherwise adds a fresh object to the SAME
`WeakSet` `authorizeCloudAsk` uses and returns the same `CloudAskGrant` type. One set, one
`assertGrant`, no cast anywhere (Guard 3's forbidden `as CloudAskGrant` / `as unknown as` / `as
any` shapes stay the only forge shapes to deny), and it **never consults `ai_task_routes`**: an
agent reading through the gateway is not Cloud Ask, so the owner's Cloud Ask switch is neither
required nor implied. `authorize.test.ts` pins that a structural look-alike fails `assertGrant`;
Guard 8(c) pins that exactly two non-test files name the function — the definition and
`agent/tools.ts`.

*Budgets, enforced for the first time.* Per `correlation_id`: ≤ 6 calls
(`READ_TOOL_MAX_CALLS_PER_REQUEST`) and ≤ 30 000 cumulative chars
(`READ_TOOL_MAX_CHARS_PER_REQUEST`, summed from `chars_returned`) — the constants ADR-066 defined
with zero enforcement sites now have one, in `agent/budget.ts`, evaluated before dispatch and
returned on every response as `budget {calls_used, calls_max, chars_used, chars_max}`. Per agent: ≤
60 calls per rolling minute (`AGENT_TOOL_CALLS_PER_MINUTE`). The seventh call, the call that would
cross 30 000 and the 61st in a minute are refused with a token-shaped `error_class`
(`budget_calls_exceeded`, `budget_chars_exceeded`, `rate_limited`) — and **a refusal is an audit row
too** (§7). The order of checks in `agent/tools.ts` is fixed: input parsed through the tool's Zod
schema (`input_invalid`) → admission (`agent/budget.ts`: trust → the permission
`READ_TOOL_PERMISSION` names → rate → calls → chars) → dispatch → audit; a refused call reads
nothing and is not charged. **Admission is atomic** (adversarial review, finding A): the count and
the audit write happen in one short transaction under two Postgres advisory locks — the agent's
id, then the correlation id, always in that order — so a fan-out of concurrent calls serialises
and the seventh sees six rows, never zero (a route test fires twenty at once and gets exactly six
200s; a hundred across fresh correlations get exactly sixty). An admitted call is *reserved* as a
`completed` row with zero chars before the lock is released, the tool runs outside the lock (a lock
held through a tool would pin one pool connection per waiter and starve the dispatch of its own),
and the row is settled with its real chars or failure class afterwards — the one UPDATE the gateway
ever makes to the audit table. The budget is keyed on `(agent_id, correlation_id)`, not the
correlation id alone: a correlation id is agent-supplied, and two agents naming the same uuid each
get their own budget (finding R2). The char budget therefore counts settled output; its overshoot is
bounded by the call cap times one output, never by concurrency.

*The gateway's own narrowing of what a search or an item read may name* (adversarial review,
finding B). `searchPersonalItems` and `getItemContext` serve the trusted client six entity types,
two of which an agent must never see: `mail_message` (ADR-054 — attacker-authored subjects and
sender names) and `inbox_item` (a capture's raw text). `AGENT_SEARCHABLE_TYPES = task | note |
event | project` is what the gateway passes to either service; an absent `types` means those four,
an explicit request for any other type is refused `input_invalid` before anything is read, and the
search results are filtered to the set again on the way out. Guard 8 pins that `agent/tools.ts`
names the constant. This is what makes the registration disclosure — "never … see your memories,
health or mail" — true rather than aspirational.

*The manifest.* `GET /agent/manifest` is the stable, machine-readable contract and the only
thing an external runtime needs: `contract_version` (`AGENT_CONTRACT_VERSION`, bumped whenever a
tool, an action, a budget or a manifest field changes shape), the agent's own id/name/trust
level, the three budgets as literals, `validation: "server-side"` (every input is re-validated
through Zod; the JSON Schema is descriptive), each tool with its permission, its sensitivity
(`titles | bodies | third_party_text` — published, never interpreted by the gateway) and
`input_schema`/`output_schema` produced by zod 4's native `z.toJSONSchema` (a schema test proves
every tool and action schema converts without throwing), each action from `ACTION_REGISTRY` with
`requires_approval: true` as a literal, and the agent principal's current grants. **External-agent
compatibility is this document, not an adapter**: OpenClaw, Hermes, a LangGraph graph or an
internal runtime binds the manifest; none of them is named in code; the runtime is replaceable
because the contract is versioned and the state (§3) is Personal OS's.

**6. PROPOSALS THROUGH THE ACTION FRAMEWORK — AND AN AMENDMENT TO ADR-078 §6.** `POST
/agent/actions` accepts `AgentActionCreateSchema` — a per-action discriminated union in the
`createVariant` idiom with `reason` REQUIRED, `correlation_id` required and `client_uuid`
optional, and with **no** `source`, `source_ref`, `principal` or `reverses_request_id` (an undo is
the owner's tap, never an agent's). The route calls the same `createActionRequest` the owner's
route calls, with an attribution argument in place of the eight literals: the row is written with
`principal = 'agent'`, `source = 'agent'`, `source_ref = agent.id`, `agent_id`, `correlation_id`,
after the trust check (`propose`) and the `agent` principal's grant check for the action's
permission — and, for an action that names an *existing* row (`AGENT_TARGET_ACTION_IDS`:
`archive_calendar_event`, `archive_task`, `complete_task`, `reopen_task`), a second check for
`context.read`: the row's `input_summary` echoes the target's title, so without that grant a bare
`task_id` would read a title the agent may not read (adversarial review, R11); a create action
names no existing row and needs only its write grant — through the same read-only `prepare` and
the same `pending` insert. From there the
row is indistinguishable in lifecycle from an owner's: it expires after 24 hours, the owner
approves or cancels it in the Action Center, `approve` re-parses the stored input and re-checks
the grant under the row's principal (§4), execution is synchronous and single-use inside the
owner's request (ADR-078 §4). **There is no agent approve route** — Guard 8(d) — and an agent
bearer presented to `POST /actions/:id/approve` is simply not a device token (ADR-082), so it is
refused before the handler runs. `GET /agent/actions[/:id]` and `POST /agent/actions/:id/cancel`
see the agent's own rows only, projected through `AgentActionItemSchema` (never the frozen
`input`, never the reason echoed back); a foreign id answers **404**, never 403, so an agent
cannot enumerate another principal's rows by probing.

*ADR-078 §6 amended.* That section holds that `source` and `reason` are "client-authored, never
model-authored". For `source = 'agent'` the reason is **agent-authored**: it is the agent's own
sentence, and it may have been written by a model. It is therefore treated as **untrusted display
text**, end to end: control-stripped and bounded (≤ 160 chars) at the gateway like an owner's;
never interpreted by the server; and on the approval sheet rendered quoted under the overline
"Agent says" in the secondary tone, while the sheet's own *why* line is the fixed sentence "An
agent proposed this. Review it as you would any request." — the reason is never the Why line and
never rendered as an instruction to the owner (§9). The rest of §6 stands: the sheet still shows
what will change from the frozen input and risk/reversibility from the registry, and no model
output becomes an action by any path other than an owner-registered `propose` agent whose
proposal the owner then taps.

**7. AUDIT, RETENTION, EXPORT, LOGGING.** *Audit.* The read side is `agent_tool_calls` (§3):
every call, completed or refused or failed, with tool name, status, error class, chars, duration
and correlation — the owner's activity screen shows what the agent TRIED, not only what it got.
The write side needs no new table: an agent's proposal is an `action_requests` row with
`agent_id` set, ADR-078 §4's audit row. `GET /agents/:id/activity` merges the two, newest first,
as `AgentActivityItemSchema` (a discriminated `tool_call | action_request`), and the client groups
by `correlation_id` into "Read: Today · Calendar → Proposed: Create calendar event → Approved →
Result". *Retention.* `agent_tool_calls` joins `retention.cleanup` on the 30-day window the
`*_sync_runs` tables use (`AGENT_TOOL_CALLS_RETENTION_DAYS`); the job imports `agentToolCalls` and
never `agents`, and a source pin in `retention-cleanup.test.ts` holds it there. `agents` and
`action_requests` are never swept: under ADR-024/080 the row is the only evidence, and a revoked
agent's row is what keeps its old proposals attributed. *Export.* Neither agent table is in
`GET /export` (§3); `export.test.ts` pins the top-level key set. *Logging.* Every gateway line is
ids, tool names and classes only (`agentId`, `toolName`, `correlationId`, `status`, `errorClass`)
— never a title, a reason, an input or an output. The raw token appears exactly once anywhere, in
the `POST /agents` response body; `serializeErrorForLog` already scrubs `Bearer …` and every
"invalid header value" message (the 10.2 hotfix), so a malformed token cannot reach a log line
through an error; and a log-capture test in the `memories.test.ts` idiom proves no `posa_` string
lands in the stream.

**8. GUARD 8.** Appended to `apps/api/src/ask/ai-egress-guard.test.ts` after Guard 7, in Guards
5–7's structure. **(a)** The agent modules — `agent/**`, `routes/agent.ts`, `routes/agents.ts`,
`plugins/agent-auth.ts`, `read-models/agents.ts` — import neither the AI SDK nor a provider package;
no memory module or table (`MEMORY_TABLE_IDENTIFIER`); no academic module or canvas table **except**
`agent/academic-tool.ts`, the one projection ADR-070b permits, which only `agent/tools.ts` may

`isPermissionGranted(`; no health or mail read model or table; no credential, consent or device
table (`OFF_LIMITS_TABLE_IDENTIFIER`, `OFF_LIMITS_DEVICES_IDENTIFIER`); no queue token
(`\bboss\b|pg-boss|_QUEUE\b`); never `approveActionRequest` or `setPermissionGrant` — an agent
proposes, the owner approves, the owner grants; and the only write verbs are

half of every lane is denied by a narrower rule than "an AI lane" (`ask/authorize.js` and

file, other read model or worker file imports an agent module or names an agent table (`agents` in a

— and the exemption is proven non-vacuous by asserting the sweep does name it. **(c)**
`authorizeAgentRead` is named by exactly `ask/authorize.ts` and `agent/tools.ts`. **(d)**

**10. WHAT IS STRUCTURALLY ABSENT.** No runtime, no loop, no planner, no session store, no
vector store, no knowledge graph. No agent approve route and no agent grant route (Guard 8(a) and
(d)). No `memory.read` tool: Guard 6 is unchanged, Guard 8(a) denies every memory import and
table name to the gateway, and the disclosure the owner registers under says "never … see your
memories, health or mail" — lifting any of the three is its own ADR with its own disclosure
vintage. No health or mail tool, ever (ADR-046/054). No new model call site: Guard 1's six are
the six. No pg-boss work. No `posops_readonly` role yet — the gateway runs as `posops_app`
because it runs inside the API process under the same grant discipline the Ask lane does; a role
is a 10.10 prerequisite for any *in-process* runtime (ADR-056/066). **Nothing leaves the machine
by the gateway itself**: the gateway serves an HTTPS route on the tailnet (ADR-018) to a bearer
the owner minted; where that bearer's holder then sends the data is the owner's decision at
registration, which is why the disclosure names every class an agent can read and why the
manifest labels each tool's sensitivity.

**11. ROLLBACK AND LIFECYCLE.** `0025` is additive except for the `source` CHECK, which is dropped
and re-added wider; the pre-10.9 images write only the four original members and never reference
the agent tables or columns, so they run correctly against the post-migration schema and rollback
is image-only (`rollback-pre-10.9` tags plus the `save-release-images.sh` set, ADR-079; no schema
step), as every checkpoint since 10.1 has done. Lifecycle of the data: an agent row is created by
the owner's `POST /agents`, changed only by the owner's `PATCH` (name, trust) and `revoke`, and
never deleted; a tool-call row is inserted by the gateway and swept after 30 days; an agent's

(or expiry, or the agent's own cancel while pending), never edited after terminal, never swept,
never exported, never sent to a model. Dropping the tables later is a separate, irreversible
ADR-024/080 decision.
