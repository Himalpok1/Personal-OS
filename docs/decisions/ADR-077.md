# ADR-077 — Checkpoint 10.7: the Personal Memory & Preference Layer is explicit, owner-owned, deterministic-only and structurally invisible to every AI lane (migration 0023)

**Status:** Locked

**Checkpoint 10.7 (2026-09-17, owner-directed; four scope decisions owner-approved the same day).**
The owner's brief moves Personal OS from "understands today's context" toward "understands stable
preferences, goals and explicitly saved knowledge" — as the foundation a future agent layer would
build on, and with four principles stated up front: memory must be **explicit** (the owner knows
what is stored), **explainable** (what, why, where from), **editable** (modify, delete, disable) and
**minimal**. The brief forbids hidden behavioural tracking, automatic personality profiling,
unrestricted AI memory, a knowledge graph, a "remember everything" system and silent extraction of
personal facts. A bounded review preceded any code — four read-only lanes over the intelligence
surfaces, the data model and migration methodology, the mobile design system, and the privacy
boundary — and its findings shaped every decision below. The four scope choices the review could not
make alone were put to the owner and decided: **deterministic-only** (no memory reaches a model),
**explicit-moment suggestions only** (no behaviour-derived triggers), **two narrow links**
(`project_id`, `canvas_course_id`), and the global switch **ships ON**.

**1. THREE FLAT TABLES, TYPED COLUMNS, TWO NARROW LINKS — NOT A GRAPH.** Migration
`0023_personal_memory_layer` (level 23 → 24) adds `memories`, `memory_suggestions` and
`memory_settings`. A memory is one bounded `statement` (≤ 1 000 chars, `MEMORY_STATEMENT_MAX_CHARS`),
an optional bounded `note` (≤ 2 000), a CHECKed `kind` ∈ {`preference`, `goal`, `fact`}, a CHECKed
`source` ∈ {`user`, `suggestion`}, provenance (`suggestion_id`) and dates. Its relationships are
exactly two nullable, `ON DELETE SET NULL` foreign keys — `project_id → projects.id` and
`canvas_course_id → canvas_courses.id` — the shape `tasks.project_id` and `tasks.canvas_assignment_id`
already use and the shape ADR-074 prescribes for every further typed relationship ("its own narrow
column, never a generalization into an edge table"). There is no jsonb `detail`, no `(ref_type,
ref_id)` pair and no `relationships` table: this codebase ran the generic-relationship experiment
once (`tags`/`item_tags`, zero adoption, classified safe-to-drop at 10.0, declined again at 10.5),
and the export, bounds and reconcile discipline all assume every user-authored value is a bounded
scalar or null. `set null` rather than `cascade` because the memory is the owner's record and the
project or course it points at is context, not its reason to exist. The vocabularies are
project-controlled and closed, so they are CHECKed (ADR-050); widening one is a migration, on
purpose. Indexes: the three link columns and `(kind, updated_at)` for the Memory Center's list.

**2. DELETE MEANS DELETE.** `memories` is the only user-authored entity with no `archived_at`.
`DELETE /memories/:id` and `POST /memories/delete-all {confirm: true}` are real row deletes (never
`TRUNCATE`, which the runtime role is not granted). Under ADR-024 (no backups) that is unrecoverable
by design; `GET /export` is the one undo, so memories join the export's user-authored core
(ADR-059) as the flat row — ids only, never the resolved project/course names — and the UI copy
says so before the confirm. Nothing ever auto-deletes a memory: `retention.cleanup` is untouched
and a source pin holds it there. The `memory_suggestions` decision table and the `memory_settings`
switch are plumbing (like `client_uuid`) and stay out of the export.

**3. NOTHING WRITES A MEMORY BUT THE OWNER.** `POST /memories` writes `source = 'user'` (the field is
not client-suppliable), and `POST /memory-suggestions/:key/decide {decision: "remember", statement}`
writes `source = 'suggestion'` with the statement the owner saw or edited — the server never
composes stored text on the owner's behalf. No parser, sync job, heuristic or worker file may
insert here (Guard 6, §6). `PATCH /memories/:id` may change kind, statement, note and the two links;
it can never change `source` or `suggestion_id`, because provenance is what makes a memory
explainable. A non-null `project_id`/`canvas_course_id` on a write is checked for existence first
(`400 validation_failed`), mirroring 10.5's assignment-link pre-check. Every memory therefore
answers "what is stored, why, where from and since when" from its own row: statement, kind, source
(+ the suggestion key's evidence line), `created_at`, `updated_at`.

**4. SUGGESTIONS ARE COMPUTED, NEVER STORED; ONLY THE OWNER'S ANSWER PERSISTS.** The rule, quotable
and enforced: *a suggestion trigger is permitted only if (i) it is computed at request time from
columns that already exist and that the owner can already see on a screen, (ii) it is about a
specific row or entity, never about the person's habits, (iii) the sentence shown cites those rows
so the owner can verify it, and (iv) nothing is persisted except the owner's explicit answer.
Anything that needs a new event log, a counter, an interaction timestamp or an inference about the
person is behavioural tracking and is forbidden.* 10.7 ships exactly one trigger, `project_goal`: an
unarchived project the owner gave a `goal` and that has no `goal` memory linked to it, offered as
"Would you like me to remember this?" with the evidence "From the goal you set on <project>". The
owner's answer is a `memory_suggestions` row keyed `project_goal:<project id>` with `status` ∈
{`accepted`, `dismissed` (offer again after `ask_again_after`, 14 days), `never`} — **no statement
text is stored on that row**, so "never ask again" cannot become a second copy of what the owner
declined to remember. Rejected on the record: "you work best in the evening" from `completed_at`
histograms (an inference about the person — automatic profiling) and "snoozed to 9 AM three times
this week" (needs a snooze history that does not exist; creating one is tracking). The suggestion
surfaces at the explicit moment (saving a project goal) and as at most one card in the Memory
Center — never as a recurring Today card.

**5. MEMORY INFLUENCES RECOMMENDATIONS DETERMINISTICALLY, BY EXPLICIT LINK, AND SAYS SO.** Memory
reaches Focus Now and the daily briefing exactly where ADR-072/075 already merge data the API may
not merge: on the client, through `packages/core`. Two new context reasons join the closed
`FocusNowReason` vocabulary — `matches_preference` and `supports_goal` — at **+15 points each**
(below the +25 context tier, an order of magnitude below any urgency rung, so memory can reorder
ties and never outrank urgency), with a new closed source `memory` and the deterministic "why"
naming the memory itself ("You said: I work best in the evening"). Matching is by **typed link
only** — a memory's `project_id` equals the row's project, its `canvas_course_id` equals the
assignment's course — never by text similarity; there is no inference. A merged task+assignment
row receives a memory bonus once. The academic base score stays the server's number verbatim
(ADR-072 §4). The briefing reads a working-hours preference into `freeBlocks`' existing
`dayStartHour`/`dayEndHour` bounds and labels the line's source `Memory`. These reasons live in
core/client code only and never touch `AcademicPriorityReasonSchema` — the `.strict()` wire enum
the deployed versionCode-31 client parses — so no installed device can blank. When the global switch
is off, the composers treat memories as absent.

**6. NO MEMORY TEXT REACHES A MODEL, A JOB OR A PUSH — STRUCTURALLY.** Memory is never a section
of `GET /today` (both AI collectors build from `buildTodayResponse` alone, so a `memories` key
there would reach the Daily Brief prompt by construction); it is its own route and read model.
**Guard 6** in `apps/api/src/ask/ai-egress-guard.test.ts` — Guard 5 copied and parameterised —
pins that no non-test file under `apps/api/src/{intelligence,ask,focus,brief}` — nor the three AI
route files `routes/{ask,briefs,focus}.ts` that own a model call's request-scoped inputs — names a
memory table binding or table name or imports the memory read model or `@personal-os/core/memory/*`; that no
other file under `read-models/` imports or re-exports the memory module or names the tables (the
one-hop evasion that would put memory in front of `TodayContext`'s three inputs); that no file
under `apps/worker/src` names the tables (no job, no push, no retention sweep); and that the memory
route and read model import neither the AI SDK nor an AI lane. `TodayContextSchema` and
`BriefInput` are unchanged and `.strict()`. Lifting this boundary is a future ADR that must also
publish a new `ASK_TODAY_CONSENT_FROM` vintage and disclosure so the owner re-consents (the 9.7
mechanism). Logging is counts-only: `"statement"` joins the core logger's forbidden-field fragments,
`serializeErrorForLog` withholds a `DrizzleQueryError`'s message outright (drizzle-orm quotes every
bound parameter in `Failed query: … params: …`, so a transient Postgres failure during an INSERT would
otherwise log the statement — found and reproduced by the 10.7 adversarial review, and pre-existing
for every user-authored write), and two log-capture tests prove no memory text appears in any line
across the CRUD cycle and across a simulated driver failure. Memories do **not** join
`GET /search` in 10.7 (ADR-065: nothing joins without its own privacy argument — and
`searchPersonalItems` is the declared future read-only agent interface). Sensitive content is not
classified: the field is bounded free text stored in the owner's own database, with a byte-pinned
"never sent to an AI model" line beside the editor and a warn-only credential-shape check
(`memoryCredentialWarning`, over the same anchored `redactSecrets` shapes Ask uses) that shows a
caption and never blocks a save.

**7. THE GLOBAL SWITCH GATES USE, NOT STORAGE, AND SHIPS ON.** `memory_settings` is a CHECKed
singleton (`id = 'singleton'`) because no settings table exists and `ai_task_routes` row-presence is
a model-consent idiom that would need a fake model id for a feature that never calls a model.
`enabled = false` makes the composers treat memories as absent and stops suggestions being offered;
CRUD, list, export and delete stay available so turning memory off can never trap the owner's data.
It ships ON (owner decision): nothing exists until the owner adds it, nothing leaves the machine,
and forcing a toggle before the first "Add" is friction with no privacy gain. This is deliberately
different from Cloud Ask's ship-OFF, which guards egress.

**8. AUTH AND API SHAPE.** Memory routes are Tailscale-perimeter-only like notes, tasks and projects
(ADR-029); device-token auth remains reserved for device/notification endpoints. Routes:
`GET /memory-settings` · `PATCH /memory-settings` · `GET /memories` (paginated, filter by kind/link)
· `GET /memories/:id` · `POST /memories` (201) · `PATCH /memories/:id` · `DELETE /memories/:id`
(204) · `POST /memories/delete-all` (200 `{deleted}`) · `GET /memory-suggestions` ·
`POST /memory-suggestions/:key/decide` (201 with the memory on `remember`, 200 otherwise, 409
`memory_suggestion_already_decided` on a conflicting repeat, 409 `memory_disabled` when the switch
is off). The list item resolves the linked project's and course's display names; the export does
not.

**9. ROLLBACK AND LIFECYCLE.** Migration `0023` is purely additive (`CREATE TABLE`, FKs, CHECKs,
indexes); the pre-10.7 images never reference the tables, so rollback is the frozen image rollback
(`rollback-pre-10.7` tags) with no schema step. Runtime grants arrive through
`ALTER DEFAULT PRIVILEGES FOR ROLE posops_migrator` — verified on a clone as `posops_app` (insert,
delete, `has_table_privilege` true) with no explicit GRANT in the migration. Data lifecycle: created
by the owner; edited by the owner; deleted only by the owner; exported on demand; never swept,
never synced outward, never sent to a model. If the feature is ever abandoned, dropping the tables
is a separate, irreversible decision under ADR-024 — the `tags` situation — not part of this record.

**Unchanged and reaffirmed:** ADR-018 (no new ingress), ADR-024, ADR-029, ADR-041/043 (the AI Daily
Brief is untouched), ADR-046 (health never reaches a model — the briefing's health line is
client-composed as before), ADR-050, ADR-056/066/067 (no new AI call site; Guards 1–5 unchanged),
ADR-058 (no new alert producer), ADR-059 (export widened by one user-authored entity), ADR-065,
ADR-072/075 (client-side merge; server academic score verbatim), ADR-074 (narrow typed FKs, never an
edge table).
