# ADR-078 — Checkpoint 10.8: the Agent Foundation & Action Framework — a code-defined action registry, an application-level permission layer, per-request owner approval with synchronous execution, and the request row as the audit trail (migration 0024)

**Status:** Locked

**Checkpoint 10.8 (2026-09-17, owner-directed; two scope decisions owner-approved the same day).**
The owner's brief moves Personal OS from "understands and recommends" toward "can safely prepare
and execute controlled actions", and names the foundation any future agent must go through:
Personal OS owns identity, permissions, context, memory, actions and audit history; an external
agent (OpenClaw, Hermes or other), if ever introduced, operates through this layer. The brief
forbids autonomous action without approval, hidden automation, unrestricted tool access, external
agent dependencies and large speculative frameworks. **No agent is built here** — this is the safe
tool surface, not the agent. A bounded, read-only architecture review preceded any code (five
parallel lanes: the write-surface inventory, identity/permissions/security, data model and
migration methodology, mobile UX, future-agent compatibility) and its findings shaped every decision
below. The two choices the review could not make alone were put to the owner and decided: the
`app` principal's grants **ship ON**; the registry starts with **three reversible pairs**.

**1. READS ARE TOOLS, WRITES ARE ACTIONS — TWO DISJOINT CONTRACTS.** ADR-066 §4 defined the
read-only tool contract a future agent binds (`READ_TOOL_NAMES`, every name `^(search|get)_`,
Guard 4). Writes cannot be added to it — Guard 4 forbids the verb — so the action registry is its
**sibling**, `packages/schema/src/actions.ts`, in the same idiom: a closed `ACTION_IDS` tuple,
per-id `.strict()` input and output schemas bound with `satisfies Record<ActionId, …>`, and an
`ACTION_REGISTRY` carrying, per action, `name`, `description`, `category`, `permission`, `risk`
(`low|medium|high`), `reversibility` (`none` or `via_action:<id>`), `target_type` and
`requires_approval: true` **as a literal** (§3). Action ids use a closed verb set
(`create|archive|complete|reopen`, `ACTION_ID_VERB_PATTERN`) and a test pins the two vocabularies
disjoint. A future agent binds them differently: it may *call* a read tool; it may only *request*
an action, which the owner then approves or cancels. The registry is client-safe (mobile imports
names, descriptions and risk from `@personal-os/schema`); the executors live in
`apps/api/src/actions/` behind an `ActionHandlerMap` whose completeness is checked at the type
level and by test.

**2. SIX ACTIONS, THREE REVERSIBLE PAIRS — AND WHAT IS STRUCTURALLY ABSENT.** The starter registry
(owner decision) is `create_calendar_event ↔ archive_calendar_event`, `create_task ↔ archive_task`
and `complete_task ↔ reopen_task`. Inputs are **narrowed** from the existing create schemas, never
widened: a timed, non-recurring event (no all-day form, no rule — a proposal is one concrete block)
and a one-off task (no rule — a rule generates occurrences indefinitely, a bigger decision than one
approval). `create_task` accepts `canvas_assignment_id`, the second explicit, owner-approved write
path for the ADR-074 link, existence-checked like `PATCH /tasks/:id`. Every handler calls the same
service function the direct route calls (`services/events.ts`, `services/tasks.ts`, extracted from
the route handlers with their route tests unchanged), so an approved action and an owner's direct
tap take the identical code path. The review's inventory of the write surface (~60 routes) fixed
what can **never** be registered: credential writes (AI providers, Calendar/Gmail/Health/Canvas
connect and disconnect), consent switches (`ai_task_routes`, `memory-settings`), device pairing,
primary and revoke, hard deletes (`/memories/*`), permission grants themselves, and every route
that sends data to a model (`/ask`, `/focus`, `/briefs`, `/mail-digests`, `/capture`,
`/transcribe`, `/inbox/:id/confirm`). None of these is an action id, so none can be granted,
requested or approved; Guard 7 (§7) keeps the executor from naming their tables.

**3. AN APPLICATION-LEVEL PERMISSION LAYER, NOT OAUTH — GRANTS GATE REQUESTS, NEVER
EXECUTION.** Migration `0024_action_framework` (level 24 → 25) adds `permission_grants`: one row per
(`principal`, `permission`) grant with `granted_at`, `revoked_at`, `disclosure_version`, and a
partial unique index keeping at most one **live** grant per pair. `principal` is CHECKed
`app|agent` (project-controlled and closed, ADR-050): `app` is Personal OS itself acting on the
owner's behalf from a client tap; `agent` is **reserved** for a runtime that does not exist. The
permission vocabulary is *not* CHECKed — it grows with every action checkpoint and is Zod-enforced
against `ACTION_PERMISSIONS` (the ADR-050 provider-vocabulary rule). **10.8 ships exactly two
members, `tasks.write` and `calendar.write`** — only permissions with a real enforcement site; a
read vocabulary with zero enforcement sites would repeat the pattern `docs/AGENT-READINESS.md` §2
criticises, so read permissions wait for the agent ADR that binds them. There will never be a write
member for health (ADR-046), mail (ADR-054), academic/Canvas (ADR-068) or memory (ADR-077), and no
member of any kind for AI config, devices or credentials. A grant answers one question — *may this
principal request actions that need this capability?* — and never *may it run unasked*:
`requires_approval` is a literal `true` on every registry entry, so widening it to a boolean is a
reviewed schema change with its own consent vintage, not a config flip. Revocation is `revoked_at`,
never a delete (the `devices.revoked_at` idiom), so the history of what was allowed and when
survives; `disclosure_version` is stored on the row rather than compared against a code constant
(the ADR-066 `ASK_TODAY_CONSENT_FROM` weakness, fixed here) — a widened disclosure shows a live
grant as `needs_reconsent`. Revoking a permission cancels every pending request that needs it, in
the same transaction. **The `app` principal's grants ship ON** (owner decision, mirroring
`memory_settings`): a pair with no row at all is materialised as a live grant lazily by the read
model; a revoked row is never re-seeded; the migration inserts nothing; the `agent` principal has
no grant unless the owner creates one.

**4. THE REQUEST ROW IS THE AUDIT TRAIL; EXECUTION IS SYNCHRONOUS AND SINGLE-USE.** The same
migration adds `action_requests`. There is no separate append-only log: every audit-shaped
precedent in this schema (`notification_dispatch_log`, the `*_sync_runs` tables,
`memory_suggestions`) keeps its lifecycle on the entity row as a CHECKed status with per-state
timestamps, and a transition table would be exactly the generic workflow engine the brief rejects.
Lifecycle: `pending → executing → completed | failed`, `pending → cancelled`, `pending → expired`
(after `ACTION_REQUEST_TTL_HOURS = 24`). `POST /actions` validates against the action's input
schema, checks the `app` grant, runs the handler's read-only `prepare` (target existence, the
bounded `input_summary`) and inserts `pending` with the **validated input frozen** as jsonb — the
`inbox_items.parse_result` precedent, and the one jsonb column this project has added since
ADR-077, because an input is a code-defined discriminated union keyed by the registry, not a
user-authored bag. `POST /actions/:id/approve` executes **inside that request**, in one
transaction: a single conditional `UPDATE … SET status = 'executing' WHERE id = $1 AND status =
'pending' AND expires_at > now() RETURNING` is the claim, so a replayed approval is a no-op (`409
action_not_pending`); the stored input is re-parsed through the same schema; the handler
re-checks its target under the lock (the TOCTOU window closes here, not at request time) and
writes; the row flips to `completed` (with `target_*`, `result_summary`) or `failed` (with a
token-shaped `error_class`, never prose) before commit; anything that leaves the process (the
calendar push enqueue) runs only after commit via the handler's `afterCommit`. Never pg-boss:
ADR-041/066/067 already record that owner-initiated, request-scoped work runs synchronously in the
API precisely so it can never become queued, scheduled or autonomous; an approval is a tap and an
action is a millisecond DB write. `apps/worker` is untouched. A terminal row is never edited and
never deleted; `retention.cleanup` does not touch the table (a source pin holds it there — under
ADR-024 the audit row is the only evidence). `GET /export` carries the summary columns, never
`input`.

**5. WHO REQUESTED IT — HONESTLY.** The API has no principal abstraction: device-token auth exists
only on `/devices/*` (ADR-029) and every other route is Tailscale-perimeter-only. So `principal`
records `app` — the owner, through a Personal OS client — and nothing pretends to more. Approval
is always the owner's own tap, so there is no `approved_by`. Binding approval to a device token
would be stronger than any existing write and is deferred with the agent ADR. A `client_uuid`
gives a retried `POST /actions` the existing row (the `POST /events` idiom).

**6. EXPLAINABLE — SOURCE AND REASON ARE CLIENT-AUTHORED, NEVER MODEL-AUTHORED.** A request
carries `source` (CHECKed `focus_now|briefing|academic|manual`), an opaque bounded `source_ref` and
a bounded `reason` (≤ 160 chars, control-stripped server-side) that the proposing client composes
from its own deterministic surfaces — the Focus Now explanation and the briefing are client-composed
(ADR-075). The approval sheet renders *why* (reason + source chip), *what will change* (the input)
and *risk/reversibility* (the registry) before Approve/Cancel. Guard 7 makes it impossible for an
AI lane to write a request, so no model output becomes an action in 10.8. The first product moment
is a **new** mutation — "Plan study block" (`create_calendar_event`) and "Add a task for this"
(`create_task`, linked) from a Focus Now assignment sheet. Existing one-tap mutations (Mark done,
Snooze) stay direct: an explicit tap is already the approval, and wrapping it teaches
rubber-stamping.

**7. GUARD 7.** In `apps/api/src/ask/ai-egress-guard.test.ts`: no file under the four AI lane
directories, the three AI route files, any other read model, or `apps/worker/src` may import the
action modules or name `action_requests`/`permission_grants` (bindings and snake_case names); the
action directory, routes and read model import neither `ai`, a provider package, a memory module
nor an AI lane, and name no credential, consent or device table; `ACTION_IDS` is verb-pinned and
disjoint from `READ_TOOL_NAMES`; the walk is proven non-vacuous.

**8. MOBILE.** An Action Center at `/actions` (hero with the pending count and the byte-pinned
trust line, segmented Pending / History / Permissions, `/actions/[id]` detail), reached from one
Settings → Privacy & AI card placed before Memory; a Today "Needs your approval" card rendered only
when something is pending, between the reminder notice and Focus Now (pinned in
`today-screen-order.test.ts`); an Approval Sheet on the module-store + single-root-host pattern.
"Undo" on a completed reversible action creates a new request with `reverses_request_id` — it is
itself approved, never automatic. Permission cards are consumer surfaces: capability, state chip,
usage, a tonal Revoke through `confirmDestructive` (revoke cancels pending work) and a plain Allow.

**9. ROLLBACK AND LIFECYCLE.** `0024` is additive only (two tables, one self-FK `set null`, CHECKs,
partial unique indexes); the pre-10.8 images never reference the tables, so rollback is image-only
(`rollback-pre-10.8` tags, no schema step), as every checkpoint since 10.1 has done. Lifecycle of
the data: a grant row is created by the read model's lazy default or the owner's PATCH and revoked
by the owner's PATCH, never deleted; a request row is created by the owner's proposal, advanced by
the owner's approve or cancel (or expiry), never edited after terminal, never swept, exported as
summary, never sent to a model. Dropping the tables later is a separate, irreversible ADR-024
decision.

**Unchanged and reaffirmed:** ADR-018, ADR-024, ADR-029, ADR-041/043, ADR-046, ADR-050,
ADR-054, ADR-056/066/067 (no new AI call site; Guards 1–6 green, Guard 7 added), ADR-058 (no new
alert producer), ADR-059 (export widened by the action summary rows), ADR-064 (an action-created
linked event uses the same durable `pending_push` link), ADR-068, ADR-074 (one more explicit write
path for the same narrow FK, no new relationship), ADR-075/076, ADR-077 (memory is still never an
action input and never reaches the executor).
